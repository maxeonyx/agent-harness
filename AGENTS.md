# agent-harness

A personal agent harness. Max's vision is the gist https://gist.github.com/maxeonyx/014463e0964bebd0add4b914971c492f — his own notes, and the driver. Derive what he wants from it; don't treat a sentence in it as a rule. Build the right thing in the spirit of what he said, not what he literally said. `vision-critique.md` is an outside review of the gist that does exactly this: evidence, not a ruling.

The repo was reset on 2026-10-16 (NZT). The earlier attempt is the unconnected branch `v1` (plus `forked-subagents`, `handoffs`, `provider-cache-probe`): evidence of what earlier agents tried and measured, none of it accepted by Max, and none of its process or framing carries over.

## What is settled

- The full vision has many aspects that interact pairwise, so it is built up incrementally: prototype a part against only a few of the other aspects, accept imperfect products, integrate, and repeat until the whole behaves well along every dimension. (High confidence.)
- No permission prompts in the harness. An environment is defined with its permissions; extending them means changing that definition, possibly by another agent. (High confidence; he calls prompts a bad abstraction.)
- No tests in the repo except truly black-box end-to-end scenarios Max can run and watch as a demonstration. Otherwise agents test manually by using the harness. (High confidence.)
- The goal is foundational software as well as Max's own harness: it covers all the essential complexity and relentlessly minimises everything beyond it, across the whole vertical stack. (High confidence; rewriting down to the machine code is a far stretch goal.)

## How the work runs

The process is the harness's own agent model, run by hand on Claude Code until the harness can run it; then the work moves onto the harness.

- **Tasks and scopes.** Each piece of work is a task given to one agent, ending in a result: its last message, saying what the parent needs to know. A parent launches a scope of tasks and makes no further decision until every result is in. A task may add siblings to its own scope.
- **Roles** (`.claude/agents/`). The orchestrator is the session Max starts, at medium effort or lower; it holds the direction and launches every scope. It also defends the process: forward progress on every dimension and backward progress on none, mistakes undone, and old things cleaned up as new ones replace them. A `designer` (xhigh) decides a model; an `engineer` (medium) builds. Only the orchestrator launches designers, because design at high effort everywhere burns Max's usage before he gets what he wants; the exception is a designer starting one that hasn't seen its design, for the independent review the design process asks for.
- **Direction comes from design; execution is cheap.** What to build next is back-chained from the vision to what Max actually wants. Building is fail-fast: try to get it right first time, expect to have built the wrong thing, try again. Checks are `cargo fmt` and `cargo clippy`, nothing more; engineers spend their time building, not testing.
- **Models first.** The core concepts are Rust types in one crate; everything else is written in terms of them. When a mechanism is built, ask how the same concept applies to every other aspect: ideally each concept exists once. An engineer who finds the model wrong, or finds itself building a second mechanism for an existing concept, stops and returns that as its result instead of redesigning. The core model is `crates/core` (package `harness-core`); read its crate docs first.
- **Spikes, then integration.** A spike exercises one thesis against a few aspects, on a branch, and is never merged: its result carries what it learned. Integration into `main` is clean and complete, and deletes what it replaces.
- **Parallel streams.** Each engineer works in its own clone, `~/agent-harness-workspace/ah-<branch>`, owns the region of the repo its task names, and merges its own PR with a merge commit. A conflict outside that region is returned to the orchestrator, not resolved.
- **Trying it costs nothing.** `node dev/drive.mjs up PORT` starts a throwaway test brain whose every role runs on the scripted model, which answers from a script in the chat with no model call (verbs in `crates/provider/src/scripted.rs`). `chat`, `settle` and `log` start a chat on it, wait for it and print its transcript; `page` drives and screenshots its page as Max does, failing loudly with the page's errors. Its top comment says how. For one real API call on Max's login: `cargo run -q -p harness-provider --bin harness-api -- GET /v1/models`. Which commit a brain was built from (`+dirty` for uncommitted changes): `harness-brain --version`, the first line of its log, and `source` in its `/view`.
- **Tool output.** A harness agent's `bash` or `grep` result that was cut ends by naming a file holding the whole output: `read` or `grep` that file instead of running the command again.
- **The page's scripts** (`crates/face-web/src/page/*.js`) are ES modules: a name is private to its file unless exported, and each file's imports say where every name it uses lives. A new file is served at `/page/<name>` with no other edit. Top-level code may use only `base.js` and other modules' `function` declarations; anything else is not initialised yet (`Cannot access 'x' before initialization`).
- **Short contexts.** A task is sized to fit one context. The orchestrator keeps its state in `ORCHESTRATOR.ignore.md` in its clone, so a fresh orchestrator resumes from that and `git log`.
- **Max's time.** The orchestrator brings him only what he alone knows: materially different shapes, how consequences rank, what he actually wants. It batches these. When he's away, a question for him goes to the `max-advocate` agent, and only what it says is his alone waits. Every integration lands with a demo under `demos/` that he can run and watch. He reads one dashboard, kept current as work lands: what to read and decide, what's running, the plan's progress, and the architecture of `main` in diagrams. It lives in `~/agent-harness-workspace/report/index.html`, served at https://mx-hv-mj.local:4330/.
