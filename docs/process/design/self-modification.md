# Self-modification — the shell / soft-middle boundary — design scoping

Provisional; built stage by stage per `README.md` (why → what → interactions → summary). **Stages: why (user-involved) · what, interactions, summary (agent-drafted, unreviewed).** Derives from `source-notes/tech.md`.

**Terminology guard (the user corrected an error here):** *"core"* in this project means **the stuff finalized/incorporated from experiments** — a *maturity* axis, not a layer, and not "the Rust implementation". A plugin can be core; you don't know whether something is core until its experiment is done. The layering axis below (**shell** vs **soft middle**) is *orthogonal* to core-ness.

## Summary

The north star is rapid iteration on the harness itself, on whatever machine it happens to be running — without source control, without deployment, without even files. Anything that is a plugin is edited directly in memory and shared immediately over the same mechanism the harness already uses to share its data. Two things bound that. Some of the harness cannot be loaded at runtime or is depended on by something outside the process, so a thin outer shell has to be compiled separately; and the very first thing the user hit with a previous harness's self-modification was an agent self-edit that instantly bricked it, so the rule is live editing but **never live bricking**. Note the axis: shell versus soft middle is a *layering* distinction, entirely orthogonal to the maturity distinction that the word "core" carries in this project — a plugin can be core, shell code can be wholly unproven, and neither answers the other's question.

The boundary is the design. Reading across the user's own sketch, what makes something shell is not that it is compiled and not that it is important — it is that **other things depend on its shape**: a protocol is depended on by a peer process, an API by whatever implements it, a rendering framework by the content drawn into it, a tool schema by a conversation that already contains calls made against it. The soft-middle items are uniformly things that *fit into* a shape someone else defines. So the test is: if changing it changes a contract that a warm session, a peer process, or a stored row depends on, it is shell; otherwise it is soft middle, and should be, because the principle is to keep the shell as thin as possible. The test predicts the sketch, with one apparent failure that turns out to be the most important thing here — tools are soft middle, yet a tool's schema goes into the system prompt, which is exactly a warm-session contract. The resolution is that the contract is not "the schema is fixed forever" but "**a session's schema snapshot is fixed for that session's lifetime**", which adds a rider to the test: soft-middle things whose shape leaks into a warm contract must have that shape **recorded per session**, so the contract lives with the session rather than with the code. That rider is nearly free, because the session record already has to contain everything the model saw.

The constraint underneath is what happens when the soft middle is swapped beneath a session whose system prompt already describes it. Keeping the old contract could mean keeping the old *code* running, which fights the north star hardest in exactly the situation self-modification exists for, where the session doing the editing is the session that wants to test the change. What dissolves it is that the note asks for the old *calls* to remain usable, not the old code: **pin the schema, run the newest implementation.** The system prompt stays byte-identical, the cache stays warm, existing calls stay valid, and the behaviour behind them is current. That resolution also deletes most of the machinery the word "pinning" suggests: the schema snapshot is already a recorded fact, calls are validated against it, **dispatch is not versioned**, and no superseded plugin code has to be retained for a warm prompt to stay honest. A reload classifies itself before deciding what it may do — schema-identical changes are adopted immediately by everyone with no cache consequence and should be the overwhelming majority; schema-additive changes are equally safe but simply unusable by a warm session whose prompt does not mention them; schema-breaking changes cannot be adopted without lying to the session, so they take an explicit cache break, best spent through the handover flow. A cache break is available on purpose and is deliberately not the normal path.

Never-live-bricking is a ladder rather than one mechanism. Load-time validation is cheap and ends the stupid failure the scar was made of — a syntax error taking down a running harness. Exercising the code on load, via plugin-declared self-checks or synthetic invocation, helps and is not sufficient, because nothing at load time catches a plugin that only breaks under real use. Quarantine is what happens on failure and is strictly better than rollback, because nothing was ever swapped in. Auto-rollback covers faults that appear after activation, and it has a prerequisite the notes do not mention: you have to know **what to blame**, since rolling back the wrong thing is its own outage. Running each plugin somewhere a fault has a name is what makes attribution possible, which means a **per-plugin isolate** is a safety mechanism serving never-live-bricking, and lands on that why's priority rather than on the security why's — the hard sandbox's credential and module restrictions are a separate concern and stay lowest, exactly as the user ranked them. And the ladder needs one rung the plugin system cannot supply: the flow that must never break is the flow that lets you fix a break, so if the tools that edit and reload plugins are themselves plugins, recovery has to be a **shell** capability that does not go through the model at all — a CLI path that starts the harness with the shell plus the last known good plugin set. The CLI is already shell, so this costs no exception to the boundary.

The shell's own half is a gated rebuild and relaunch: the new build must compile, start, and satisfy its migrations before it becomes the thing that runs, and graceful shutdown means finishing in-flight requests, remembering the tool calls that were about to run, and continuing them afterwards, with many concurrent sessions resuming onto the new code. Rollback here is structurally harder than for a plugin, because a plugin rollback happens inside a process that is still there to do it while a binary rollback happens when the new process failed to start and nothing is running to notice — so never-live-bricking the shell needs an actor that survives the shell, whether a supervisor or a small launcher holding the previous binary. Finally, there are two workflows rather than one, and the shell/soft-middle boundary is the line between them: the in-memory loop is the fast one, happening in the meta limb because that is where the live plugin set is reachable, and it needs only edit, validate, reload, roll back and relaunch, with no compiler; editing the shell means a checkout, a build and a relaunch, which the meta limb cannot host at all since it has no project filesystem, so that happens in an ordinary project limb pointed at the harness's own repository. The limb model therefore bounds the fast workflow — a project session cannot hot-swap a plugin — but it does not put the harness's source out of reach, and it is not a substitute for a safety argument about shell edits. That is what makes "keep the shell as thin as possible" a measurement rather than an aesthetic — it is the fraction of the harness that can be improved in the fast loop.

## Why

### 1. Rapid iteration and self-hosting — *desire (the north star)*

The point is rapid iteration and development *of the harness* — on whatever machine it happens to be running, no matter which one. Without bothering with source control, without deployment, without even files. Anything that is a plugin gets edited **directly in memory and immediately shared, over the same mechanism the harness already uses to share its data.** "The more's in TS, the more is boosted by self-modification." Forward: bootstrap self-modification as fast as possible (basic loop → agent edits code → relaunch onto the new code) so the harness starts building itself early.

### 2. But bounded — a thin shell must be compiled separately — *correctness/capability*

We can't do that for everything. The outer skeleton — the hosting binary, the web package / wasm module, the platform-specific "how data gets from A to B" — needs to be compiled separately. We should make that shell as **thin as we can**, and use Rust and/or JavaScript for it.

### 3. Never live-brick — *safety (top priority)*

The scar: the very first thing hit with Pi's self-modification was an agent self-edit that *immediately bricked the harness*. Really dumb. So: live editing, but **never live bricking** — exercise plugin code on load as much as possible, and revert to the old version if the new one crashes. You must be able to change yourself without dying.

### 4. Stable APIs the soft middle conforms to — *correctness (this is what makes self-mod safe *and* cache-stable)*

The shell provides stable **APIs / frameworks**; the soft middle provides **implementations that fit them**. The load-bearing example: the **context-provider API** — a plugin reload must not cause a cache break, which *implies* a stable API that context providers conform to (the system prompt, including tool defs, stays put across a reload; old tool calls remain usable until a deliberate handover/compaction or an explicit cache break). Same pattern for the replication protocol and CLI-argument contributions: the *framework* is shell, the *contributions* are soft middle.

### 5. Sandbox / secrets — *nice to have, lowest priority*

Sandboxing agent-edited plugins away from credentials (auth flow outside the plugin; hand back a pre-authenticated fetch wrapper; no arbitrary node modules) is nice, but the user does not personally prioritise it. Lowest on this list.

## What

The boundary sketched below is the spine of this design, so the "what" starts from it rather than restating it. Three things need developing on top: a *test* for classifying things the sketch does not list, since every future experiment will need to answer "shell or soft middle?"; the mechanics of changing the soft middle underneath a session that is already warm, which is where the interesting constraint lives; and the mechanics of changing the shell, which means rebuilding and relaunching the harness with something to fall back to. The meta limb ties the two together, and it turns out to divide them rather more cleanly than expected.

### The boundary — as the user sketched it

**Shell** (thin, compiled separately; provides frameworks, APIs, transport, rendering engines):

- website package, wasm module, hosting binary
- the CLI — though CLI *arguments* may have contributions from the soft middle
- getting data from place to place; the **replication protocol** (enforced by the shell); the framework one must write replication-protocol and CLI-arg contributions within
- the **provider API** — the interface provider implementations must fit
- the **rendering framework** for the TUI and for the web
- stable APIs generally (e.g. the context-provider API in #4)

**Soft middle** (plugins, edited live, rapid iteration):

- provider *implementations*
- tools, user tools, business logic
- **pretty much all UI content — even the TUI content** (not the rendering framework), because UI especially wants rapid iteration
- UI elements for a provider's usage/cost/etc — given a place in the UI, kept as flexible as possible
- exact data *formats* may be provided or extended by the soft middle (the transport and protocol are shell)

Principle: make the shell **as thin as possible**; push everything you want to iterate rapidly into the soft middle.

**How the editing happens: the meta limb.** Self-editing happens via the **"meta limb"** — the agent operates on the harness itself from that limb, rather than on a project. This is the concrete home of #1: the plugin-editing-in-memory that gets shared over the harness's own data mechanism is work done in the meta limb.

### A test for what belongs in the shell

The sketch is a list of examples, and lists do not classify new cases. Reading across it, what the shell items have in common is not "compiled" and not "important" — it is that **other things depend on their shape**. A protocol is depended on by a peer process. An API is depended on by whatever implements it. A rendering framework is depended on by the content drawn into it. A tool-definition schema is depended on by a conversation that already contains calls made against it. The soft-middle items are, uniformly, things that *fit into* a shape somebody else defines: a provider implementation fits the provider API, a tool fits the tool framework, TUI content fits the rendering framework, a CLI argument contribution fits the CLI framework.

So the test: **if changing it changes a contract that a warm session, a peer process, or a stored row depends on, it is shell.** Otherwise it is soft middle, and should be, since the principle is to make the shell as thin as possible. There is a second, duller reason something can be shell — it physically cannot be loaded at runtime, like the hosting binary or the wasm module — but that is a platform fact rather than a design judgement, and it applies to a small and shrinking list.

The test predicts the sketch's own classifications, with one apparent failure that turns out to be the most important thing in this design. Tools are soft middle, but a tool's *schema* goes into the system prompt, and the system prompt is exactly a contract a warm session depends on. By the test, tools should be shell. They are not, and they should not be — tools are the single thing most worth iterating rapidly. The resolution is that the contract is not "the schema is fixed forever"; it is "**a session's schema snapshot is fixed for that session's lifetime**". Which means the test needs a rider: soft-middle things whose shape leaks into a warm contract must have that shape **recorded per session**, so the contract lives with the session rather than with the code. That is a property the session record already has to provide, which is what makes the rider cheap.

The same rider explains the sketch's line about data formats — that exact formats may be provided or extended by the soft middle while the transport and protocol are shell. An extension is additive inside an envelope the shell owns, so old rows stay readable; the envelope is the contract and the contents are not.

Two things this test deliberately does not decide. It says nothing about *maturity*: a plugin can be core, and shell code can be entirely unproven. That is the terminology guard at the top of this doc, and the test is orthogonal to it. And it says nothing about language: the sketch says use Rust and/or JavaScript for the shell, so "shell" does not mean "the Rust part" any more than "core" does.

### Changing the soft middle underneath a warm session

This is where the design has an actual constraint rather than a preference. From `source-notes/tech.md`: we want to keep the context the same for as long as the KV cache is still valid, so if we relaunch or reload plugins we still want the system prompt to remain the same — but the system prompt contains the tool call definitions, so "we still want the old tool calls to be usable by the agent until the next handover/compaction or the next cache break". A cache break should be *available* as an option for a plugin reload, but explicitly not the normal path: "Cache break should be an option for plugin reloads though. but not normal path, it should rather be explicit."

There is a genuine tension between two of the whys hiding in that. Why #1 wants rapid iteration: the agent edits code and wants to see the effect *now*. Why #4 wants the warm session's contract stable. If keeping the contract stable means the warm session keeps running the *old code*, then a bug fix does not take effect until the next compaction — which is close to the opposite of what the north star asks for, and it would be maddening in exactly the situation self-modification exists for, where the session doing the editing is the session that wants to test the change.

The reading that dissolves it is that the note asks for the old *calls* to remain usable, not for the old *code* to keep running. So: **pin the schema, run the newest implementation.** The system prompt stays byte-identical, the cache stays warm, the agent's existing calls stay valid — and the behaviour behind them is current.

What that actually requires is less than it first appears, and it is worth being exact, because the obvious reading of "pinning" invents a lot of machinery that the resolution above removes. A session needs the **schema snapshot** its context was built with, and it already has one: the walking-skeleton ruling requires that everything the model sees be derivable from the session record, and that `/dump` reproduce the model's view, so the tool definitions that went into the system prompt are recorded facts already. Incoming calls are then validated against that recorded snapshot. **Dispatch itself is not versioned** — every session, warm or cold, reaches the newest implementation, which is the whole point of the resolution. And no plugin *code* version needs retaining to keep a warm prompt honest, because the prompt's content is in the record rather than reconstructed from the plugin.

Three cases fall out, and they are worth naming because a reload has to classify itself into one of them before deciding what it is allowed to do:

A **schema-identical** change — the implementation changed, the declared interface did not — is adopted immediately by every session, warm or not, with no cache consequence. This should be the overwhelmingly common case, and it is the one that makes rapid iteration feel rapid.

A **schema-additive** change — a new optional parameter, a new tool — is safe to adopt for the same reason, with the caveat that a warm session simply cannot use the addition, because its system prompt does not mention it. New sessions get the new definition. If the addition matters to the warm session, that is what the explicit cache break is for; and this is the same shape as the change-notice problem in context-updates, where a tool with a changed schema is the one case that needs full content injection rather than a bare notice.

A **schema-breaking** change — a removed or renamed parameter, a removed tool — cannot be adopted by a warm session without lying to it, because the session's prompt still advertises something that is gone. The honest answer is the explicit cache break, and the Interactions section argues it should be spent through the handover flow, since compaction already owns the machinery for building a successor context and telling it what is *different*. The alternative — keeping the superseded implementation runnable for whoever is pinned to it — costs retention, version-keyed dispatch and a rollback story for two divergent code paths, all to serve the case the classification says should be rarest. It is not obviously worth it, and it is the "should the schema-breaking case keep old code runnable" question below. Preferring the handover is what keeps the rest of this design small.

Classifying the change requires comparing declared schemas across versions, which is mechanical and cheap, and it means a reload is a decision rather than an event. It also means the reload path needs a way to say "this one needs a cache break" and have that be a deliberate, user-or-agent-visible act rather than a silent cost.

### Never live-bricking

The scar in why #3 is an agent self-edit that immediately bricked the harness. The notes' instinct is right and modest: "I guess we probably want to exercise plugin code on plugin launch as much as we can", and if the new version crashes, revert to the old one. "While we want live editing, we don't want live bricking."

That is a ladder rather than a single mechanism, and the rungs have very different strengths.

Load-time validation is the cheap rung and catches the majority of real self-edit disasters: does the module parse, does it evaluate, does it export what it claims, do its declared schemas validate. A syntax error taking down a running harness is the stupid failure the scar was made of, and this rung ends it.

Exercising the code is the rung the notes ask for without saying how. The honest options are plugin-declared self-checks — a plugin ships something the harness can run on load — and a synthetic invocation of its entry points. Both help and neither is sufficient, because no amount of load-time exercise catches a plugin that only breaks under real use. This is a proposal rather than a ruling, and its limits should be stated openly so nobody mistakes a green load for a working plugin.

Quarantine is what happens on failure: the failing version is marked bad and does not become active, the previous version stays active, and the agent that made the edit is told what went wrong in enough detail to fix it. Quarantine is strictly better than rollback because nothing was ever swapped in.

Auto-rollback covers failures that only appear after activation, and it has a prerequisite the notes do not mention: you have to know **what to blame**. A fault raised inside a tool invocation is attributable to that plugin trivially. A fault that surfaces later, or in the event loop, or as corrupted state, may not be attributable at all — and rolling back the wrong thing is its own outage. The mechanism that makes attribution possible is running each plugin somewhere a fault has a name: **a per-plugin Deno isolate**, which bounds blast radius and lets the harness say "this plugin faulted" rather than "something faulted".

Two things worth separating here, because `source-notes/tech.md` mentions them in one breath and they have very different priorities. The **isolate** is a safety mechanism serving why #3 — it is what auto-rollback's attribution requires, so it lands on why #3's priority and should be built early. The **hard sandbox** — no arbitrary node modules, no reach at credentials — is the security property of why #5, and it stays exactly where the user put it: lowest. Building isolates early therefore contradicts nothing about his ranking; it just means the isolate was never really a security feature in this design. Keeping the two fused is what makes it look like a conflict.

And the ladder needs one rung the plugin system cannot provide. The flow that must never break is *the flow that lets you fix a break*. If the tools that edit and reload plugins are themselves plugins — which the sketch's classification implies, since tools are soft middle — then a sufficiently bad edit removes your ability to repair it. The way to keep both the sketch and the guarantee is to make **recovery a shell capability that does not go through the model at all**: a CLI path that starts the harness in a safe mode with only the shell plus the last-known-good plugin set, and a way to roll a plugin back from outside. The CLI is already shell. This costs nothing, requires no exception to the boundary, and means the worst case is a manual command rather than a lost harness. Proposal, not in the notes.

### Changing the shell: rebuild and relaunch

The compiled path is the other half, and the notes describe the intended flow: implement the basic loop, then the agent can edit the code and probably use a tool call to relaunch onto the newer code — for the binary itself as well as for plugins — with the binary supporting "some kind of state scheme so that we can launch back into the same session". Backend server cache ids and similar must not be ephemeral; they are tracked in the database by session, so a relaunch can seamlessly continue. The brain may be running the agent loop for many sessions at once, and on relaunch it should simply continue them. Graceful shutdown means waiting for all in-flight API requests to complete, remembering that we were about to run tool calls, and then running those and continuing after the relaunch.

The resume-after-a-long-gap question is left open in the notes with the hedging intact, and it is worth preserving exactly: "Perhaps if it's been more than an hour, then (if interactive) we ask the user whether we should continue other agents. If it's the brain in server mode, it should definitely just continue. Actually - I don't think that's so clear. Probably this should be optional too. The brain relaunching within an hour can continue but beyond an hour, first client would have to decide whether or not to resume other agents."

Two design points need adding. First, a relaunch has a gate: the new build must have compiled, must start, and must be able to open the database and satisfy its migrations before it becomes the thing that runs. Migrations themselves are operator-lifecycle's subject; the requirement here is only that a relaunch does not proceed on hope.

Second, rollback for a binary is structurally harder than rollback for a plugin, and the difference deserves stating. A plugin rollback happens inside a running process that is still there to do it. A binary rollback happens when the *new process failed to start*, at which point there is nothing running to notice. Something outside must hold the fallback: either an external supervisor (`source-notes/tech.md` already contemplates re-parenting to systemd or Task Scheduler when detaching a GUI, so the supervisor is not a new idea in this project), or a small launcher that keeps the previous binary and restarts it if the new one does not reach a healthy state within a window. The notes do not specify which, so this doc does not either — but the requirement is unavoidable: **never-live-brick for the shell needs an actor that survives the shell.**

One small thing that is easy to omit and annoying to retrofit: a deliberate self-relaunch has to be *distinguishable in the record* from a crash, or the analytics surface will report the harness as unstable every time the agent improves it.

### The meta limb, and the two workflows the boundary actually divides

The sketch names the meta limb as where self-editing happens: the agent operates on the harness itself from that limb rather than on a project. Because a session is bound to exactly one limb, and because crossing a limb boundary is always fresh, in-memory plugin editing is necessarily a *separate session* from the project work that provoked it — the live plugin set is reachable from the meta limb and nowhere else.

It is tempting to read a safety property into that, and worth being careful not to. What the limb model bounds is the *fast* workflow only: a project session cannot reach in and swap a plugin under a running harness. It emphatically does not mean the harness's guts are unreachable from a project session, because the very next paragraph puts shell editing in an ordinary project limb, and editing the harness's source is self-modification by any reasonable reading. Nor is relaunch meta-limb-exclusive: `source-notes/agent-harness-design.md` has the brain offering its own tools "always available regardless of limb". So the honest claim is narrow — live plugin swapping is confined by construction — and it is not a substitute for thinking about what a project session pointed at the harness repo can do.

Developing this reveals that there are really *two* self-modification workflows, and the shell/soft-middle boundary is the line between them — the meta limb hosts one side of it rather than being the divider. The in-memory workflow is why #1 in its purest form: the agent edits a plugin in the meta limb, in memory, "without bothering with source control, without deployment, without even files", and the change is shared immediately over the same mechanism the harness already uses to share its data. There is no build step and no restart; the reload machinery above is the whole story. The compiled workflow is different in kind: editing the shell means a checkout, a build, and a relaunch, which means source control and files are back, and the meta limb cannot host it at all — an in-process meta limb has no project filesystem to check out into. That work happens in an ordinary project limb pointed at the harness's own repository, and relaunch is a brain-native tool it calls when the build is good, rather than a second session in the meta limb.

The notes do not draw that distinction explicitly; `source-notes/tech.md` treats "edit a plugin or the harness implementation itself, build and reload autonomously" as one capability. I think separating them clarifies a lot: it explains why "make the shell as thin as possible" is not an aesthetic preference but a direct measure of how much of the harness can be improved in the fast loop, it gives the phrase "the more's in TS, the more is boosted by self-modification" a precise meaning, and it tells the experiment that there are two distinct things to demonstrate with two distinct risk profiles. It also means the meta limb's tool set is smaller than it first appears: edit, validate, reload, roll back, and relaunch. It does not need a compiler.

The last piece is that plugin edits propagate, and it is the reason the database is the right home for plugins in the first place. Why #1 asks for an edit to be shared immediately over the same mechanism the harness already uses to share its data — which is the database and its replication — so a self-edit reaches other faces and other brains the way events do, making "the harness edits itself" a distributed change rather than a local one. That is mostly a stage-3 concern with topology and persistence, but it has one consequence worth stating now: a plugin version has to mean the same thing everywhere, so plugin versions need globally unique identity for the same reason durable rows do.

### Putting it back together

The design is one boundary and one constraint. The boundary: anything whose *shape* other things depend on — a protocol, an API, a framework, a schema — is shell, and everything that merely fits into such a shape is soft middle, which is nearly everything, which is the point. The constraint: the soft middle can be swapped underneath a session whose system prompt already describes it, so a session validates calls against the *schema* it recorded, runs the *newest implementation*, and only takes a cache break when a change is genuinely breaking and someone asks for it explicitly. What is worth noticing is how little that costs — the schema is already a recorded fact, dispatch stays unversioned, and no old code needs keeping — because the naive reading of "pinning" invents a retention and dispatch apparatus that the resolution makes unnecessary. Around it sit the safety mechanisms, which exist because the failure mode is losing the ability to fix yourself: validate and exercise on load, quarantine rather than swap, roll back with attribution good enough to blame the right plugin, and keep a recovery path in the shell that never goes through the model. The shell's own version of all this is a gated rebuild-and-relaunch with something outside the process holding the previous binary. And the fast half happens in the meta limb, while the slow half happens in an ordinary project limb pointed at the harness's own source — the boundary being, in the end, a boundary between two editing workflows.

The thesis is that an agent can edit the harness and continue working, without bricking it and without breaking the sessions that are already warm. Falsifiers, in roughly descending order of how much they would hurt: recording the schema turns out not to preserve the cache in practice, so every reload costs a cache break and self-modification stops being free; running the newest implementation behind a recorded schema produces behaviour the warm session cannot make sense of, forcing the old-code reading and with it both the slow-iteration cost and the retention apparatus this design just deleted; fault attribution proves too weak for auto-rollback to be safe, meaning the only honest response to a fault is a full rollback of everything changed since the session started; or the relaunch path cannot resume many concurrent sessions cleanly, which turns every shell improvement into an interruption and pushes the shell/soft-middle line for reasons of pain rather than design.

It touches invariant 1 most directly of all the invariants here — a plugin is agent-edited code, and the auth flow stays outside it with a pre-authenticated wrapper handed back, so credentials never reach the thing the model wrote. Invariant 2 matters in a way that is easy to miss: a plugin reload is a context change, not a reason to call the model, so a reload must never trigger a request. Invariant 5 carries plugin storage: plugin versions are durable data, replicated like every other durable row, and the schema snapshot a session validates against is part of that session's durable record. Invariant 8 and the terminology guard sit together — shell-versus-soft-middle is a layering question and core-ness is a maturity question, and a plugin can be core. Invariant 9's drain semantics are what a relaunch's graceful shutdown is made of. And invariant 4 keeps the meta limb honest: it lives inside the brain process and must still behave like a limb.

## Interactions

The obvious thing to say about this design is that it touches everything, and the obvious thing is the least useful, so it is worth disposing of first. Every experiment's result eventually has to be classified as shell or soft middle. But that is what the classification test is *for*: it exists precisely so the question does not need pairwise negotiation with fourteen designs, and going through them one at a time would change nothing that either experiment does. So the "interacts with every experiment" candidate is **discarded as an interaction** and kept as a checklist item at promotion time, with two exceptions where the classification genuinely changes what a sibling builds — multi-client-ui and oauth-credentials, both below.

What this experiment owns is the boundary and the swap. Concretely: the classification test, the schema-pin-run-newest-implementation constraint and the three-way change classification that goes with it, the safety ladder from load-time validation through quarantine to attributed rollback, the shell-side recovery path that never goes through the model, and the split into two editing workflows. What it defers is most of the machinery those depend on.

### The tension it resolved, and why it is not in the cache cluster

`INTERACTIONS.md` does not list this design in the cache-state prediction cluster, and that is deliberate rather than an oversight. This design is about iteration speed on the harness itself; cache enters it once, as a **constraint** — a reload must not force cache expiry — and not as a motive. The tension between why #1's rapid iteration and why #4's stable contract was resolved by recording the schema and running the newest implementation, and that resolution is still pending a ruling (the "pin the schema, run the newest code" question below). The reason it does not join the cluster is that self-modification needs the cache state *observed*, not *predicted*: the claim is that a reload leaves the system prompt byte-identical, and whether it did is answered directly by the provider's reported cached-input tokens on the next request. There is no bet being placed, so there is nothing to predict. **This experiment therefore does not depend on the provider cache probe** — a useful independence, given how much else does.

### Context updates: the same event, classified twice

This is the strongest connection in the doc, and it runs both ways. Context-updates' why #1 names self-modification as one of the two designs that *manufacture* routine mid-session change, so the changes this design produces are the input to that design's classification. Working the two together shows the three reload classes here map cleanly onto that classification, and — the useful part — they agree rather than conflict.

A schema-identical reload is not a context change at all, so there is nothing to notify and nothing to decide; this is the case that makes rapid iteration feel rapid and it is invisible to context-updates entirely. A schema-additive reload that adds a tool lands on context-updates' finding that a *new* tool is rebuild-only, because a model cannot call something absent from the frozen tools array — which is exactly what this design already says when it observes that a warm session simply cannot use the addition. A schema-breaking reload maps onto notifiable-with-full-injection, since the schema is the action-enabling content, with the explicit cache break as the alternative. So the scoping call is that **this design classifies its own reload and context-updates decides what the session is told**, and neither needs a mechanism the other does not already have.

Two riders. Context-updates' rule that changeable option sets must not be declared as schema enums applies here too, since a reload is one of the things that can change such a set. And the harness-voice question — that notices and briefings are the harness speaking and must not be attributed to the user — carries a reload notice as well, which is one more argument for one mechanism rather than three.

### Compaction: where an explicit cache break should be spent

The connection is narrower than the parked note implied, and sharper. A plugin reload is emphatically *not* a compaction, and the whole point of recording the schema is that it does not become one. The single place the two meet is the schema-breaking case, and this is where compaction earns a real scoping win: if a cache break is being taken deliberately, a bare rebuild is the wrong way to spend it, because compaction already owns the mechanism for constructing a successor context, including the briefing that says what will be *different* — and a changed tool schema is precisely a difference a successor needs told. Routing the break through the handover is what lets this design decline the alternative altogether, and declining it is what keeps retention and versioned dispatch out of the design. So the dependency runs deeper than a preference: compaction's handover is load-bearing for self-modification's simplicity, and it is in the questions below.

The dry-run rebuild has a small consequence here too: because the briefing's diff is computed against the successor's system prompt, a plugin version change that landed since the last rebuild surfaces at the handover whether or not any notice was ever appended. The handover is the reconciliation point for reloads as much as for edited files.

### Limb model: one mechanism, two names

The meta limb is limb-model's to define as a kind; what it carries is this design's, and the What already concludes it needs no compiler. The connection worth developing is that a plugin reload changes the *tool set*, and the tool set is limb-declared — so "a session records the schema snapshot it was built with" is a statement about the limb's snapshot rule, not a separate mechanism. The two designs describe one thing from two ends, and neither can weaken its half: if limb-contributed context stopped being a snapshot taken at a known boundary, there would be nothing for a session to validate calls against. What this design inherits is narrower than it first looks: because the live plugin set is reachable only from the meta limb, a project session cannot hot-swap a plugin — but shell editing happens in an ordinary project limb, so the limb model bounds the fast workflow and not self-modification as a whole. Assumed from limb-model, not tested here.

### Persistence: why the database, and how little retention is actually needed

The notes float the storage question with a hedge — "However, I think we store plugins in the DB, perhaps?" — and the hedge is worth keeping, because the reason the note gives for it is not the reason that survives.

The reason that survives is why #1's sharing requirement. A plugin is edited in memory and **immediately shared, over the same mechanism the harness already uses to share its data** — which is the database and its replication. Storing plugins anywhere else means building a second distribution mechanism alongside the one that already works. That forces the database without any argument about retention, and it is why plugin version identity has to be globally unique for the same reason durable rows are.

Retention is the weaker reason, and after the What's resolution it is close to unnecessary. Since a session's schema snapshot lives in the session record and reloads run the newest implementation, no superseded plugin *code* has to be kept for a warm prompt to stay honest. Old versions are worth keeping for rollback and for the audit trail of what the agent did to itself — both real, neither load-bearing on the cache — and if the schema-breaking case is ultimately served by a handover rather than by divergent code paths, nothing needs a retention rule keyed to session lifetime at all. `INTERACTIONS.md` records the data-lifecycle classification that persistence owns; what this design contributes to it is small.

Two smaller requirements this design asserts and persistence owns. A deliberate self-relaunch has to be distinguishable in the record from a crash, or the analytics surface reports the harness as unstable every time an agent improves it. And plugin version identity has to be globally unique for the same reason durable rows are, because plugin edits replicate. **Durability is assumed from persistence and not tested here**; what this experiment tests is that the pin means what it claims at the wire.

### Operator lifecycle: the compiled half is mostly not this experiment

This design's whys are inherited by operator-lifecycle at the deployment level, but the mechanisms cannot be, because a dead process cannot roll itself back. Working that through gives the largest scoping call in this doc: **the supervisor, staged activation, two-phase verification, snapshot-before-migrate, the downgrade barrier and version negotiation all belong to operator-lifecycle, and this experiment assumes them.** The two demonstrations named in the What survive, but the second one's content shrinks to what is genuinely self-modification's — the agent-initiated trigger, and the outcome that many concurrent sessions resume onto new code without being asked anything. The staged-update mechanism underneath is another experiment's to prove. If that split is wrong, this experiment gets substantially larger, which is why it is in the questions.

Layered-shutdown belongs to the same handoff. Its why #3 says frequent relaunch is what makes bounded shutdown urgent — a claim about this design's effect rather than a requirement on it — and the exit-code semantics it defines are read by operator-lifecycle's verification step, not by anything here.

### Modular components, topology, oauth, multi-client-ui

Modular components decides what a plugin is *constructed* as, and `INTERACTIONS.md` places construction and injection there. What this design needs from it is specific and load-bearing in two places: if a plugin reads nothing ambient and receives everything at construction, then a reload is re-construction with new code and the same ports, which is what makes the schema-identical case cheap, and a fault has a name, which is what attribution for auto-rollback requires. The shell-plus-last-known-good recovery mode is then not a special path but one more composition of the same tree — the one-builder-two-compositions property doing real work.

Topology's contribution is that plugin edits propagate over the same replication mechanism as session data, which makes a self-edit a distributed change — and, per the Persistence entry above, is the actual reason plugins live in the database. The mechanism is topology's and persistence's; what this design owns is only the consequence that a plugin version must mean the same thing on every brain, which reduces to the globally-unique identity requirement above. The classification itself is settled by the sketch — the replication protocol is shell, its data formats may be soft middle — and needs nothing further.

Oauth-credentials is the worked example of why #4 rather than a separate topic. Provider implementations are soft-middle plugins, the auth flow stays in the shell, and the destination-bound pre-authenticated fetch *is* a stable API the soft middle conforms to. So the fetch abstraction is oauth's to design and this design owns only the boundary rule it exemplifies. Multi-client-ui is the other place classification changes something: putting almost all UI content in the soft middle is a constraint on how that experiment exposes its state model, since the content has to be replaceable without recompiling. One-directional, and small, but it does change what gets built.

### The genuinely empty cells

Forked-subagents is thin: plugin edits happen in a meta-limb session, which is an ordinary subagent, so the hierarchy is used rather than stressed and nothing about either design changes. User-turn is close to empty here — the user editing prompts and skills in band is user-turn plus context-updates, and the process-improver stakeholder's wish for rapidly iterable prompts is this design's why #1 applied to content rather than code, which is a resemblance and not a connection. Cancellation-economics has nothing to say. Recording those is worth the sentences, because it means three experiments can proceed without waiting on this one.

## Questions for review

- **My classification test.** "If changing it changes a contract that a warm session, a peer process, or a stored row depends on, it is shell" is derived from your sketch's examples, not from anything you said. It predicts your list, but it initially misclassifies tools as shell, and I rescued that with the rider that such things must have their shape recorded per session. Is the test the right one to hand to future experiments?
- **Pin the schema, run the newest code.** This is the biggest call in the doc. `tech.md` says the old tool *calls* must remain usable; I read that as being about the declarations rather than the implementations, because the alternative means a warm session keeps running stale code, which fights why #1. If you meant the stronger thing — old code for warm sessions — say so, because it is what brings back version-keyed dispatch, retention of superseded plugin code, and two divergent code paths to roll back, all of which this reading deletes.
- **Should the schema-breaking case keep old code runnable at all?** I have come down against it: a schema-breaking reload takes an explicit cache break, spent through the handover flow. The alternative serves the rarest of the three reload classes and costs the whole retention-and-dispatch apparatus to do it. If you want superseded versions runnable, say so, because that is the single decision that most changes the size of this design.
- **Recovery in the shell.** I have proposed a CLI safe-mode path (shell plus last-known-good plugins) and out-of-band plugin rollback, so that bricking the editing tools cannot cost you the harness. It keeps your sketch intact — the editing tools stay soft middle — but it adds a shell surface you did not list.
- **Who holds the fallback binary?** Never-live-bricking the shell needs something that survives the shell: an external supervisor (systemd / Task Scheduler, which you already contemplate for detaching) or a small launcher that keeps the old binary. The notes do not choose; I have stated the requirement without choosing either.
- **Two workflows, not one.** I have split in-memory plugin editing in the meta limb from compiled shell editing in an ordinary project limb pointed at the harness repo. `tech.md` treats them as one capability. If you agree, the meta limb needs no compiler and the experiment has two demonstrations rather than one.
- **Shell edits are not confined by the limb model, and nothing currently confines them.** The meta limb bounds live plugin swapping, but any project session pointed at the harness's repository can edit its source, and relaunch is brain-native rather than meta-limb-only. I have deliberately *not* proposed a guard, since you do not want permission prompts — but I want to flag that the confinement is narrower than it first appears rather than let it read as a safety property.
- **Load-time exercise is weaker than it sounds.** Plugin self-checks and synthetic invocation are my proposals for "exercise plugin code on plugin launch as much as we can", and neither catches a plugin that only breaks under real use. Is quarantine-plus-rollback carrying more of the safety weight than you intended?
- **A structural question about this doc.** Your boundary sketch reads as the natural opening of this "what", and I have left it in place above rather than folding it in, since you wrote it. It may want merging at summary stage.
- **Does the compiled half's machinery belong wholly to operator-lifecycle?** I have scoped it that way: the supervisor, staged activation, verification, migrations and the downgrade barrier are assumed from there, leaving this experiment the in-memory plugin work plus the agent-initiated relaunch trigger and the resume-onto-new-code outcome. The two demonstrations survive but the second one shrinks a lot. If you want this experiment to prove the staged update too, it gets substantially larger.
- **Should an explicit cache break be routed through the handover flow?** If a break is deliberate, compaction already owns the machinery for building a successor context and for telling it what is *different* — which a changed tool schema is. Making a bare rebuild the alternative path would mean two ways to spend the same cache break. This is the same decision as the schema-breaking question above, seen from compaction's side.
