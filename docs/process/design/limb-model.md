# Limb model — design scoping

Provisional; built stage by stage per `README.md` (why → what → interactions → summary). **Stages: why (user-involved) · what, interactions, summary (agent-drafted, unreviewed).** Derives from `source-notes/agent-harness-design.md` (the spine), `source-notes/configuration-model.md`, and the limb references in `source-notes/agent-hierarchy.md`, `tech.md`, and `context-updates.md`. ("Limb" is still a placeholder name — candidates: workspace, context, environment, sandbox.)

A framing note the user corrected: the limb is **not** best understood by contrasting it with the brain (they are almost always the *same process*), and it is **not** a security boundary. Security is a non-concern in this project — a nice-to-have tacked on at the end, never the top. So the whys below are about *environments*, not isolation.

## Summary

A limb is a **place** — the environment an agent is acting in. The reason the concept exists is that context and action are place-specific in a way that does not average out: the user has one environment for developing this project, one for editing its meta documentation and agent instructions, one for the harness's own configuration, and each carries its own tools and its own *load-bearing instructions*. An agent that implicitly acted across all of them would need every environment's instructions at once, which does not work well. So a session exists with respect to exactly one limb, and acting somewhere else means launching a subagent *there* rather than borrowing that place's tools mid-session. To act in a context you must be in it.

The place is authoritative over three things, and they are three faces of "what it is like to act here" rather than a feature list. It declares **which tools exist** — the brain adds its own small always-present set and otherwise neither filters nor rewrites, and it does no processing of limb tool calls at all, it dispatches them. It decides **what context reaches the model** from its domain, covering both the static material (in-repo and per-machine AGENTS.md files, checked-in agents and skills) and execution-shaped context only it can produce, like truncating a large tool output or appending LSP information to a call. And it owns **how execution happens**: filesystem, shell, git, processes.

The thing it deliberately does not own is the session record, which is the brain's. So the limb's contribution arrives in two shapes with different rules. The **layer hierarchy** — AGENTS.md files, checked-in agents and skills, the declared tool set — is evaluated once, at session start or at a rebuild, and recorded there: a warm session's context is immutable, so there is no later moment to change it in, and compaction has to be able to dry-run a successor's hierarchy before the successor exists, which means composition must be a deterministic function of recorded inputs. **Execution-shaped** context — truncating a large tool output, appending LSP information to a call — is produced when the tool runs and recorded as an event alongside its result, which is an append rather than a change. Both satisfy the requirement that everything the model sees be derivable from the session record, for the same ordinary reason: the text is in the record either way. On top of that sits a proposal — that limb contributions arrive as *labelled* blocks naming the layer that produced them, with truncation recorded as an event rather than performed silently — which turns the "can the brain manage cost and debugging without seeing what the limb injected" question into a labelling requirement rather than a visibility dilemma, since the brain always has the text.

The design's second load-bearing idea is that a limb holds **no durable session state**. The brain owns the record; the limb owns only the running world — its processes, its filesystem, its open tools. That is why the notes can say flatly that a limb with no brain connection does nothing and might as well not exist: there is nothing in it to lose. So the brain keeps a limb as an ordinary **configuration row** — which machine, which directory, which kind, plus per-limb settings like a display name, resource limits, and which agent types may use it — and both reconnecting to a limb and re-creating one after a brain restart are just acting on that row rather than special recovery paths. What the row does *not* carry is how to make a place that does not exist yet: a fresh clone needs a source repository, a ref, and setup steps. That construction spec is the **factory's** real content, and it is the one thing here the stored row does not already give us.

The notes give six example kinds, and read as an enum that list is arbitrary. Read as points in a space it is three independent dimensions: *where it runs* (inside the brain process, a local subprocess, or another machine), *what it can do* (everything, read-only, or nothing), and *how long it lives* (with the brain, with a connection plus a grace period, or permanently). The named kinds are just useful corners. Expressing the dimensions rather than the enum is what stops every new combination — a read-only remote limb, which is an obvious thing to want when inspecting a production host — from needing a new type name. The pure-model limb is the one that proves what the concept is about: no filesystem, no tools, no injected context, and still a valid limb, so "limb" means authority over the tool set and the context, and zero is a legal value for both.

Remote is one of the largest motivators and the sequence is specific: the harness SSHes in, ensures a compatible copy of its own single binary exists there, runs it in limb-server mode, has it expose a port, and connects through a tunnel — after which a replica of the harness is running remotely for the sole purpose of providing a limb to an agent on the local one. The agent deals with none of it: no SSH, no quoting, no plumbing, just a subagent launched into that place. Two consequences worth carrying. Authentication comes free, because the tunnel means the port is only ever reachable from the far end of a connection the user was already authorised to make — SSH *is* the credential, which is why the permanently-available limb-as-a-service kind is genuinely different and has to authenticate for itself. And the lifecycle timer has to belong to the *limb*: the case being handled is the brain disappearing, and a timer on the brain cannot fire in a world where the brain is gone. So a remote limb survives an ungraceful disconnect in case of reconnection and then self-terminates on loneliness — reaping its process trees on the way out, since ownership-based cleanup is the only cleanup allowed.

One part of this design does not exist yet, and the honest thing is to say which. **Context layers** — user, user-and-machine, machine, project, user-and-project — are sketched as types with no precedence order, and the source note that would define them is marked incomplete and deferred. Three things can be said without inventing the missing design. Composition must produce a serialisable result at a known moment, so it is a deterministic function of recorded inputs, which rules out resolving layers lazily as the model asks for things. A changed limb is a *rebuild-only* change, never an append, because the limb determines the hierarchy — so together those mean layer composition is a pure function evaluated at a small number of known boundaries rather than a live reactive system, which is a large simplification derivable from decisions already made. And precedence and merge are plausibly the same machinery as configuration precedence and merge, which is another experiment's, and solving it twice would be the mistake. What cannot be guessed is the precedence order itself, and what happens when two layers contribute AGENTS.md-shaped instructions that disagree.

Two smaller things are unowned and matter. Materialisation — executing that construction spec — must be *observable*, because "the agent is stuck" and "the agent is waiting on a four-gigabyte clone" look identical from outside. And nothing in the notes says who deletes the clone, which makes the factory a disk leak in a long session; the shape that fits is that the creating scope owns the created limb and cleanup happens at scope completion — but conditional on the working copy being clean, with an explicit keep option, because destroying uncommitted work is exactly the mess the teardown story exists to prevent.

The thesis the experiment has to test is that "a session exists with respect to one limb" is designed behaviour and not a slogan: that a real limb can declare a tool set and compose a real context hierarchy, that the brain can store and rebuild what the limb defined, and that crossing into another place is genuinely just launching a subagent there. It would be falsified by layer composition turning out to need live evaluation, which breaks rebuild and compaction's dry-run together; by the brain being unable to manage cost and debugging even with labelled blocks; by the remote path leaking SSH to the agent through quoting, latency or error messages, which fails the transparency requirement outright; or by the stored row proving insufficient to reconnect to a limb or re-create one. "Limb" is still a placeholder name, and the design's own logic argues against *sandbox* (it is explicitly not a security boundary) and against *runtime* (it over-suggests execution when the load-bearing part is context); the two sentences any candidate has to survive are "a session exists with respect to one X" and "X-local context".

## Why

### 1. The limb is an environment; context and action are place-specific — *correctness/quality (PRIMARY)*

An agent should carry only the instructions and tools for the environment it is acting in. The story, from the user's own work on this project: he has several distinct limbs — one for testing and developing the project, one for editing the meta documentation and agent starting instructions, one for the harness config itself. Separate environments, with separate tools and — the key part — **separate, load-bearing instructions**: a project's instructions are what the model needs to edit and act *correctly* in that environment.

If a single agent implicitly acted across all environments, it would need the instructions for all of them at once, and that does not work well. So we split environments. An agent acts within one, carrying only that environment's context; to act in another environment it interacts with an agent that is acting with respect to *that* environment and has the appropriate context — which the first agent does not need to know. A clean way to separate various kinds of work.

Mechanism (confirmed): a session is bound to exactly one limb; switching context means launching a fresh subagent in the other limb, never borrowing another limb's tools mid-session. To act in a context you must be *in* it.

### 2. Environments are varied, not just filesystems — *desire, from three concrete wants*

The same abstraction covers genuinely different kinds of environment: filesystem environments; an environment with *nothing* in it (pure model, no tools/context); the harness itself in memory (the **meta limb**, where self-modification happens); and remote environments.

Drilling back, each of those has a want behind it rather than being a taxonomy for its own sake. The empty environment exists because the user wants a cheap answer from model memory, a baseline to compare against, and a classifier — none of which should pay for a project's instructions and tool schemas. The in-memory environment exists because the user wants the harness to edit and relaunch itself, and self-modification has to happen *somewhere*. The read-only environment exists because he wants meta-work over his own session data without write authority — `source-notes/analytics.md` asks for "a read-only tool surface or limb for meta-work" in as many words. Unifying them under "limb" is what stops each of those wants needing its own concept.

### 3. Transparent remote environments — *desire (one of the largest motivators)*

A top motivating factor. The vision: the harness SSHes into a remote machine, SCPs a binary across, runs it, has it expose a port, connects to that port via an SSH tunnel — and now a replica of the harness runs remotely, **specifically just providing a limb** to an agent on the local harness. That limb provides instructions for the folder it is in, for the user it runs under there, and maybe for the machine. Crucially it is **transparent from the agent's perspective**: the agent does not deal with SSH or quoting or plumbing — once we have set up (created) the limb in that place, the agent just launches a subagent in that environment.

### 4. Limb factory — exactly the environment you need, when you need it — *capability/desire*

We should be able to construct additional *copies* of a limb. The classic case: a fresh clone of a repo specific to a particular task; in the remote case, the same but remote. The point is having **exactly the environment you need, exactly when you need it, with all the context well-tuned for that environment only.**

### 5. One process, many locations — a memory driver, but only one — *resource*

The harness presents an interface over many filesystem/folder locations while requiring only one harness process — no need for many harness instances. Memory efficiency (one brain of moderate fixed cost + lightweight limbs + lazy, evictable LSPs; ~400–500 MB per full instance was the pain) *was and remains* a driver, but only one of several, and its size is now in doubt because multiple projects still need multiple LSP instances. Not the primary reason.

## What

A limb is a place. Everything below is either an answer to "what does the place have authority over", "what kinds of place are there", "how do you name, make, and reach a place", or "how long does a place live". The one part that does not resolve cleanly is how a place's context is assembled out of layers, and that is honestly underspecified in the notes rather than merely undecided; it is treated as such below.

### Three authorities, and one thing the limb deliberately does not own

The limb is authoritative over three things, and they are not a list of features so much as three faces of "this is what it is like to act here".

It declares **what tools are available**. The brain may add its own tools to the set — session history, sibling status, Task, Resume — but by default it does not filter or redefine limb tools, and would only do so if the user configured it to. Notably the brain does no processing of limb tool calls at all; it dispatches them. So the tool surface an agent sees is the limb's declaration plus the brain's small always-present set, and the boundary between those two is clean because one side never rewrites the other.

It decides **what context reaches the model** from its domain. That covers the static material — in-repo AGENTS.md files, per-machine AGENTS.md files, checked-in agent and skill definitions — and also execution-related context that only the limb is in a position to produce: truncating large tool outputs, appending LSP information to tool calls. The second category is the interesting one, because it means the limb is not just a context *source* consulted at startup; it shapes context continuously as work happens.

And it owns **how execution happens**: filesystem, shell, git, and all local execution. This is invariant 10's "every component owns exactly one external world" applied to the limb, and it is why the walking-skeleton ruling put environment facts like hostname on the limb's side of the ledger.

The thing the limb deliberately does *not* own is the session record. The brain stores the session context and tool set, and a session keeps a fixed context and tool set for as long as the cache is valid — persisted, so the harness can restart and continue. If we suspect the KV cache is no longer warm, the context can be rebuilt before sending the next request.

That split gives the limb's two categories of context contribution two different rules, and it is worth separating them because a single rule for both would be wrong for one of them.

The **layer hierarchy** — the static material above, plus the declared tool set — is evaluated at a known boundary and recorded there. Two independent reasons force that, and neither is about introspection. The first is the cache fact just stated: a warm session's context is fixed, so there is no later moment at which the hierarchy *could* change; the only moments are session start and a rebuild. The second is compaction's: it has to describe a successor's context before the successor exists, which means running the composition as a dry run, which only works if composition is a deterministic function of recorded inputs. Together those say the hierarchy is a pure function evaluated at a small number of known boundaries.

**Execution-shaped** context is the other category and it is not bound by that. Truncating a large tool output or appending LSP information to a call happens when the tool runs — mid-session, in a warm context — and the result is recorded as an event alongside the tool result. That is an append, not a mutation of the hierarchy, so it is compatible with an immutable warm prefix and with a deterministic rebuild.

Both categories satisfy invariant 10's requirement that everything the model sees be derivable from the session record, and they satisfy it the same ordinary way: the text is in the record. Worth being precise that the requirement is about the *completeness of the record*, not about when a value was computed — computing at request time and recording the result would satisfy it too. And `/dump` is safe either way for a reason that has nothing to do with timing: the request builder and the dump share one projection, so they structurally cannot diverge whatever feeds them.

There is an open question in the notes about exactly this boundary, filed as limb-local context opacity: the limb owns what reaches the model from its domain, while the brain owns cost, reliability and debugging — can the brain manage those without visibility into what the limb injected or filtered? I think it largely answers itself, and in a specific way. The brain necessarily has the *text*, because the brain builds the request. What it may lack is *provenance* — which layer produced which block, and what was dropped on the way. So the real requirement is not visibility but labelling: limb contributions should arrive as labelled blocks, with the layer that produced them named, and truncation recorded as an event rather than performed silently. That is a proposal of mine, not a ruling, and it is listed as a question below; but if it holds, "opaque versus declared" stops being a dilemma, because the content is always visible and only the labels are a design choice.

### The kinds of place, and what they actually vary on

The notes give six examples, explicitly not exhaustive. A **full local limb** is a subprocess in a git repo on the same machine as the brain, with filesystem, shell, git, grep, formatters, linters, tests and lazily-started LSP; it lives as long as it is connected to the brain, or until the brain exits. A **remote limb** has the same capabilities over SSH and a tunnel on another machine; its lifecycle is related to but distinct from the SSH connection, surviving an ungraceful disconnect in case of reconnect but shutting down if not reconnected within a timeout. An **in-process meta limb** lives inside the brain process and provides meta or global tools — cross-session search, agent status, config edits — with no project-local filesystem. A **remote limb-as-a-service** is a permanently available authenticated endpoint, for instance with database-backed tools. A **read-only limb** offers read, grep and glob, with no writes and no shell. And a **pure model limb** has no tools and no injected context beyond the prompt, for a cheap answer from model memory, for baseline comparisons, or for classification tasks.

Read as an enum, that list is arbitrary. Read as points in a space, it is three independent dimensions, and the space is the thing the design should express:

*Where it runs* — inside the brain process, as a local subprocess, or on another machine reached over a tunnel or an endpoint. *What it can do* — everything, read-only, or nothing. *How long it lives* — with the brain, with a connection plus a grace period, or permanently.

The named types are just useful corners: read-only is the capability dimension turned down without touching the others, and limb-as-a-service is the lifetime dimension turned to permanent. Expressing the dimensions rather than the enum matters for configuration, because otherwise every new combination — a read-only remote limb, say, which is an obvious thing to want when inspecting a production host — needs a new type name.

The pure-model limb is worth one more sentence because it proves what the concept is really about. It has no filesystem, no tools, and no injected context, and it is still a valid limb. So "limb" does not mean environment-with-a-filesystem; the invariant content of the idea is *authority over the tool set and the context*, and zero is a legal value for both. That is the strongest argument that unifying these under one abstraction (why #2) is not merely tidy.

The meta limb needs a rule that follows from invariant 10 rather than from the notes. It runs inside the brain process, which means it physically shares memory, filesystem, environment and clock with the brain. Logically it must not reach into any of that: it exchanges the same messages a remote limb does, or it becomes a back door through which limb-owned state leaks into the brain by reference. Co-location is a deployment fact; the role boundary is unaffected (invariant 4). The practical version of that rule is that the meta limb should be implementable as a *remote* service without changing anything on the brain side.

One thing that rule does *not* forbid, because invariant 10 explicitly licenses it: a co-located deployment may use the shared session state directly as the **substrate** those messages travel over. That is a transport choice, and topology treats it as the strongest substrate available in that deployment rather than as a different architecture. The prohibition is on reaching into the brain's world by reference, not on the two being close together.

### A limb holds no session state, so it is a stored configuration row

The property that makes the rest of this design cheap is a negative one: **a limb holds no durable session state.** The brain stores the session context and tool set (above); the limb owns the running world and nothing else — its processes, its filesystem, whatever tools it has open. That is what makes the notes' otherwise startling line — "Limbs that have no brain connection do nothing and might as well not exist — this is fine." — ordinary rather than reckless, and the note gives the reason itself in the same breath: a limb with no brain *does nothing*. There is no accumulated state in it to lose, so throwing it away costs nothing.

What follows is how a limb is named. The notes already answer it: a limb is currently identified by `ssh_host` — the machine it runs on, empty or local for same-machine limbs — and `directory`, the working directory or project root, and "These are stored in the brain", with the judgement that "That's likely all that's needed to connect, start, and reconnect a limb." Other per-limb configuration that may be needed is listed as undecided: a display name, which agent types are allowed to use it, resource limits.

So a limb is a **stored configuration row**. Host and directory are two of its columns; kind is another, which the type space above makes necessary — a read-only limb and a full limb over the same host and directory are two different limbs, the in-process meta limb has neither a meaningful host nor a directory, a limb-as-a-service has an endpoint, and a pure-model limb has neither. Display name and resource limits are further columns. The row may have a surrogate id or be keyed on whatever subset turns out to be unique; nothing in this design depends on which, and the brain reconnects to a limb or re-creates one by reading the row either way.

Two things fall out immediately, and both are treated below rather than being separate ideas. **Brain restart** is reading rows and reconnecting or restarting, not a recovery path. And the **factory** is not the row at all — the row says where a place is, not how to bring one into being. Making a place that does not exist yet needs a source repository, a ref, and setup steps, and that construction spec is the only genuinely new thing the factory adds.

### Context layers — the genuinely underspecified part

This is where the design does not yet exist. `source-notes/configuration-model.md` is marked "placeholder / stretch goal — very incomplete" and ends with "This area needs significant design work. Deferred." I am not going to write that design here; what follows is what the notes contain, plus the constraints that are already fixed by decisions elsewhere, plus a note on what is missing.

The provisional layer types, not exhaustive, are: **user-specific** — preferences, prompts, agent personas, skills; **user-and-machine-specific** — credentials, SSH config, shell config, per-machine user preferences; **machine-specific** — installed toolchains, available formatters and linters, environment variables, where "machine" means the user on a system rather than the whole system, since there is no use case for system-wide yet; **project-specific** — AGENTS.md, project config, ignored paths, git root, package manager; and **user-and-project-specific** — personal project preferences, custom prompts, per-project user settings.

On where that state lives and how an agent edits it, the notes sketch three answers with decreasing confidence. Project config is straightforward: it lives in the project, and the agent edits it through the project limb as ordinary files. User config might live in a brain-local limb — the brain exposing a limb-like context environment for user-level configuration that agents can read and edit. Machine config might be another limb, in the user's home directory on that machine, which fits naturally because machine context is per-user-on-system and the home directory is where that state already lives.

The open questions are the substance of the deferral, and they are real: how layers are discovered and composed; what the precedence or merge order is when layers conflict; how the brain knows what context the limb injected; whether layers should be declared to the brain so it can reason about them, or opaque; how this interacts with skills and extensions; and whether a brain-local limb for user config blurs the brain/limb boundary problematically or is a natural special case.

Three things can be said without inventing anything. First, from the hierarchy rule above: composition is evaluated at a known boundary and recorded there, so the composition function has to be deterministic and its inputs recorded. That rules out the most tempting shortcut — resolving layers lazily as the model asks for things — and it means a rebuild must be reproducible from the record. Second, and usefully, a **changed limb is a rebuild-only change**: `source-notes/context-updates.md` is explicit that a changed limb changes the limb-specific context hierarchy, that this is load bearing, and that it "shan't change without a compaction / context re-build". Combined, those two mean layer composition is a *pure function evaluated at a small number of known boundaries*, not a live reactive system. That is a large simplification and it is derivable from decisions already made. Third, `PLAN.md` already observes that this overlaps the modular-components experiment's config work — a typed schema defined once, explicit ordered sources, recursive merge for nested components, parent-to-child propagation without globals — and names them "candidates to merge when either is pulled". Precedence and merge are plausibly the same machinery as configuration precedence and merge, and solving them twice would be the mistake.

What is missing and cannot be guessed: the precedence order itself. Whether project beats user, whether a machine's toolchain facts can be overridden by project config, and what happens when two layers contribute AGENTS.md-shaped instructions that disagree. The notes do not rule on it, so this doc does not either.

### The limb factory

The factory exists to give an agent exactly the environment it needs, exactly when it needs it, with context tuned for that environment only (why #4). The classic case in the notes is a fresh clone of a repo specific to a particular task, and in the remote case the same thing on another machine.

The factory is the one operation a stored row cannot express, and saying why locates the design work precisely. Copying a row and editing its `directory` produces a row pointing at a directory that does not exist; it does not produce a clone. What is missing is not a field but a **construction spec** — where the working copy comes from (which repository, which ref), and what has to happen after it lands (submodules, dependency install, whatever the project needs before tools work). That spec is the factory's content, and it is genuinely new: nothing in the notes supplies it, and nothing else in this design needs it.

*Materialisation* is then the act of executing that spec — producing the directory, cloning the repo, ensuring a binary exists on the far machine — and it is real work with real duration and real failure modes. It is the part that has to be observable to the user, because "the agent is sitting there doing nothing" and "the agent is waiting on a 4GB clone" look identical otherwise.

Materialisation also creates state that outlives the operation, and here the notes are silent in a way that matters: nothing says who deletes the clone. Left unowned, the factory is a disk leak that a long session turns into a real problem. The shape that fits the rest of the design is that the **creating scope owns the created limb**, so scope completion is the natural cleanup point — which is why #4's teardown story from forked-subagents, applied to a resource rather than to a task. With one important exception: a working copy containing uncommitted work is precious, and deleting it because a scope ended would be exactly the kind of mess the teardown story exists to prevent. So cleanup needs to be conditional on the place being clean, with an explicit keep option, and an unclean limb at scope end is something the user should be told about rather than something the harness resolves. That is my proposal; the notes have no position.

The notes say clone; a git worktree is the obvious cheaper materialisation for the same-machine case and is not mentioned. What it gives up is worth being exact about, because the trade is narrower than it sounds. A worktree gives each place its own **working tree**, which is where the concurrent-edit problem actually lives; what it shares is the object store and refs, so the residual risk is concurrent ref updates and index contention rather than two agents editing one file. I raise it as a candidate rather than assuming it, and the question is a cost measurement rather than a principle.

### The remote limb, step by step

This is one of the largest motivators (why #3), and it is worth walking through mechanically, because the vision is specific and the details are where it either feels transparent or feels like SSH with extra steps.

The sequence in the notes: the harness SSHes into a remote machine, copies a binary across, runs it, has it expose a port, connects to that port through an SSH tunnel — and now a replica of the harness is running remotely, specifically just providing a limb to an agent on the local harness. That limb provides instructions for the folder it is in, for the user it runs as there, and maybe for the machine. The agent deals with none of it: no SSH, no quoting, no plumbing. Once the limb has been created in that place, the agent just launches a subagent in that environment.

Several details follow, and I have flagged which are the notes' and which are mine.

The binary being copied is *the same binary*, in limb-server mode. `source-notes/tech.md` is clear that the app is a single binary able to run in any mode — client, brain server, limb server — and Pi is cited as the feasibility reference precisely for this: a self-contained binary you can `scp` to a remote with no Node or npm needed on the target. That has an immediate consequence: the remote copy's *version* has to be compatible with the local brain's, so "copy a binary across" is really "ensure a compatible binary exists there", which implies a version check first and a copy only when missing or stale. Version negotiation and protocol versioning are operator-lifecycle's subject, so this design just needs to not assume identical builds. The notes do not say where on the remote machine the binary lives, nor how the remote platform and architecture are detected in order to send the right build; both are gaps.

Port selection is unspecified and needs to be, because several limbs may run on one host under one user. The mechanism I would propose is that the limb chooses its own port and prints it on startup, which the harness reads over the SSH session it already has open before establishing the tunnel. That avoids both a fixed port and a registry, and it is testable. Mine, not the notes'.

Authentication comes free in this arrangement: the tunnel means the limb's port never needs to be reachable from anywhere but the far end of an SSH connection the user was already authorised to make. SSH *is* the credential. That is worth stating only because it explains why the limb-as-a-service type is different — a permanently available endpoint has to authenticate for itself — and because it means the transparent-remote story does not need any new security design, which suits a project where security is explicitly a nice-to-have rather than a driver.

Lifecycle is the part that is genuinely distinct from the SSH connection. A remote limb survives an ungraceful disconnect, in case the brain reconnects, and shuts itself down if no reconnection arrives within a timeout. The timeout value is not specified. What is worth noticing is *whose* timer it must be: it has to be the limb's own, because the case being handled is the brain disappearing, and a timer on the brain cannot fire in a world where the brain is gone. So a limb self-terminates on loneliness. That is the same reasoning as "limbs with no brain connection might as well not exist", turned into a mechanism.

Two things about disconnect are not answered by the notes. If a long-running command was in flight when the connection dropped, its output has nowhere to go, since the brain proxies streaming output from limb to face. Whether that output is buffered for the reconnect, discarded, or the command is abandoned is unspecified — and it matters, because the walking-skeleton ruling makes the limb the owner of its process trees, so the limb is still holding a running process with a real result. And a limb that self-terminates on timeout must clean up those process trees on the way out, which is the graceful-shutdown-is-a-priority point applied to a path nobody watches.

### Lifecycle and restart

The local case is simple: a local limb lives as long as it is connected to the brain, or exits with the brain. The remote case is the self-timeout above. Graceful shutdown semantics are called out as important and as a priority; crashes are to be rare rather than designed around.

Brain restart is where the statelessness pays off. The brain works out of the SQLite database and, on restart, should pick up where it left off without requiring user interaction to resume threads. If it was interrupted while waiting on a model response, it is safe to resend and continue. If it was interrupted mid-tool-call, the tool reports something like "tool call interrupted by harness crash", and the agent reasons about state and safety itself. Limbs that were connected may have shut down; they reconnect or are restarted as needed.

Two clean consequences. Because the limb held nothing durable, "restarted as needed" is a real option rather than a hope — the brain still has the row, so restarting a limb is the same operation as starting one, and restart-after-brain-crash is not a special path. And because the *agent* reasons about interrupted tool calls, the limb does not need to journal tool-call state for recovery; it only needs to own and clean up its processes. That is a tidy division of responsibility: durability of intent is the brain's, ownership of the running world is the limb's, and judgement about what an interrupted action left behind is the model's.

The one wrinkle is orphaned processes. Process cleanup happens by ownership, never by global observation, and the owner is the limb. If the limb itself died, its children may survive it with nobody to reap them, and the harness is not permitted to go looking for them. Kernel-enforced ownership — PID namespaces or cgroups, "some kind of container maybe" — is recorded as a hedged later idea, and it is the only real answer to this case, so this design should note the gap rather than pretend the ownership rule covers it.

### The shared filesystem, from this side

Fork-by-default siblings can share one limb's filesystem, and multi-agent-on-one-codebase is poor today. The primary treatment of that problem belongs with forked-subagents, since forking is what creates it. The limb-side observation is just this: the limb is the thing being shared, so any ownership rule — instructions telling agents which workspace scope they own, or the tentative and undesigned borrow-checker-style rule on mutable workspace regions — is a *limb-level* concept, expressed in terms of paths inside a place rather than in terms of agents. And the factory is the other answer, at the cost of a fresh context. Unresolved either way; noted here so the limb model does not look like it has forgotten that it is the shared resource.

### What to call it

"Limb" is a placeholder. The candidates are workspace, runtime, context, environment and sandbox, with the design notes bolding **workspace** and **context**, which reads like a mild preference. The design's own logic argues against two of them: *sandbox* is wrong because the thing is explicitly not a security boundary, and *runtime* over-suggests execution when the load-bearing part is context. *Context* is accurate to the concept but collides badly with the vocabulary this project uses everywhere else — context window, context rebuild, context layers, context providers — and "a session exists with respect to one context" is ambiguous in a way that will cost us. *Workspace* reads best in a sentence and worst in this ecosystem, where the user's own habit is that a workspace is a multi-repo checkout containing several projects, which is nearly the opposite of one place. *Environment* is bland and accurate.

Two tests any candidate has to pass, since they are the phrases that will appear thousands of times: it must read naturally in "a session exists with respect to one X", and it must work as a modifier in "X-local context" and "X factory". Undecided in the notes, and undecided here.

### Putting it back together

A limb is a place, authoritative over the tools available in it, the context that reaches the model from it, and how execution happens in it — and deliberately not the owner of the session record, which is the brain's. Because it holds nothing durable, it can be discarded and re-made: the brain keeps it as a configuration row, so reconnecting and restarting after a crash are both just acting on that row rather than recovery paths, and the only thing the row cannot express — how to bring a place into being that does not exist yet — is exactly the factory's construction spec. Its layer hierarchy is evaluated at known boundaries and recorded, which keeps composition a pure function rather than a live system; its execution-shaped contributions are appended as events when tools run. The six named limb types are corners of a three-dimensional space — where it runs, what it can do, how long it lives — and the pure-model limb, with no tools and no context, is what proves the concept is about authority rather than about filesystems.

The thesis the experiment has to test is that "a session exists with respect to one limb" is a designed behaviour and not a slogan: that a real limb can declare a tool set and compose a real context hierarchy, that the brain can store and rebuild what the limb defined, and that crossing into another place is genuinely just launching a subagent there. It would be falsified by any of: layer composition turning out to need live evaluation, which would break rebuild and compaction's dry run together; the brain being unable to manage cost and debugging without knowing what the limb injected, even with labelled blocks; the remote path being visible to the agent in practice, through quoting, latency or error messages that leak SSH, which fails why #3's transparency requirement outright; or the stored row proving insufficient to reconnect to a limb or re-create one.

It touches invariant 1 (credentials never reach the limb, which is what makes a copied binary on someone else's machine acceptable), invariant 4 (the meta limb is co-located with the brain and must still respect the role boundary), invariant 10 (nothing crosses by reference to role-local state, and the face/limb shared-environment exception is exactly the local-limb case), invariant 3 (limb-contributed context is a projection, and labelling its provenance is what makes the other projections possible), invariant 5 (limb configuration and reconnect state are durable), and invariant 2 (a limb noticing a change in its environment must not thereby trigger a model request).

## Interactions

This design is mostly a *supplier*. Several other designs perform their work inside a limb, or rely on something the limb declares, and almost every connection has the same shape: a sibling needs the place to behave a certain way, and this design either already does or has to be told to. That makes the useful output of this stage a list of things this experiment must guarantee for others, plus one genuine disagreement where a sibling's cheapest path and this design's safest one point in opposite directions.

What this experiment owns is the place itself: the three authorities (which tools exist, what context reaches the model from this domain, how execution happens), the limb as a stored configuration row holding no session state, the three-dimensional type space and the corners it names, the factory and its construction spec, the remote bootstrap-and-lifecycle path, restart, and the rule that the layer hierarchy is evaluated at known boundaries and recorded. What it defers is everything about what an *agent* then does in that place.

### The one real disagreement: the factory versus fork

`INTERACTIONS.md` recorded a conflict between forked-subagents' fork-for-cache default and the safe answer to parallel work, and now records its dissolution into a decoupling. One half of that decoupling is this design's to state: a limb's **context** (the layer hierarchy that reaches the model, which is what decides whether a fresh start is required) is separable from its **working location** (where the bytes live). "A different limb forces a fresh context" is true because a different limb normally carries different load-bearing instructions — but a factory-made clone of the same repository carries the *same* hierarchy, so crossing into it costs a bounded prefix delta (the location fact) rather than a fresh context. Which is also why the location fact's position matters: it should sit where changing it disturbs the least prefix, and stating that is this design's obligation to forked-subagents' clone arm. The other consequence arrives from outside: keeping parallel siblings off each other's files is rooted in the shared-mutable-state problem `source-notes/open-questions.md` records, and it promotes three of the What's proposals into load-bearing requirements — materialisation must be *observable*, because a four-gigabyte clone and a stuck agent look identical from outside; cleanup ownership must be decided, because a limb-per-child pattern turns an unowned clone into a disk leak within one session; and worktree-versus-clone becomes a real cost question with a real consumer. That last one is also where the two motives can disagree: a worktree serves why #4 fully and serves the isolation want only partly.

The division is that **this experiment measures manufacture — how long it takes, whether it is observable, whether it cleans up — and forked-subagents measures the choice.** Whether fork or a manufactured limb is the better default is an agent-behaviour and cache question that cannot be answered from this side, and this doc should not try.

### Self-modification: the meta limb, and one mechanism wearing two names

The meta limb is this design's to define as a *kind*: in-process, no project filesystem, and — the rule that comes from invariant 10 rather than from the notes — obliged to talk to the brain over the same message surface a remote limb uses. What it *carries* is self-modification's: edit, validate, reload, roll back, relaunch, and no compiler, since the compiled workflow runs in an ordinary project limb pointed at the harness's own repository. That means self-modification needs no new limb kind at all, which is a pleasant result for both designs.

The connection that changes something is subtler. A plugin reload changes the tool set, and the tool set is limb-declared — so self-modification's central constraint, that a session pins the schema it was built with, is a statement about *this* design's hierarchy rule. The hierarchy rule and the schema pin are one mechanism seen from two ends: the limb's declaration is captured at a known boundary, the brain records it, and the record is what a warm session's system prompt describes. Nothing new is needed on either side, but neither design can weaken its half without breaking the other's claim.

There is also a smaller question the two designs share. `configuration-model.md` suggests user-level configuration might live in a brain-local limb; the meta limb is an in-process limb providing meta and global tools including config edits. Those may well be the same thing, and if they are, the "does a brain-local config limb blur the boundary" open question is answered by the meta limb already existing. Raised below rather than assumed.

### Context updates: the limb reports, the brain decides

Two directions, and both are already partly named in the What. What this design supplies is that a changed limb is the canonical rebuild-only change (the limb determines the hierarchy, so there is no append that fixes it), and that per-limb tool sets are one half of the progressive-disclosure answer — a subagent in a specific limb simply never carries tools irrelevant to that place. What it consumes is the policy: change *detection* lives in the limb, because watchers watch a filesystem and the limb owns the filesystem, while classification and what the session is told are context-updates'. **This experiment owns reporting change and nothing about responding to it.**

One connection is worth developing rather than naming, because it turns a proposal in the What into a requirement. Context-updates computes its notices as a diff between the world and what the context actually contains, which requires the context to record what version of what it holds. That left-hand side is exactly the labelled-provenance proposal here — limb contributions arriving as labelled blocks naming the layer that produced them, with truncation recorded as an event rather than performed silently. So labelling is not only the answer to the limb-local-context-opacity question; it is what makes another design's central mechanism computable at all. If labelling is rejected, context-updates loses its diff.

### Compaction: determinism, and the boundary a successor never crosses

Compaction has to describe its successor's context before the successor exists, which means running a dry-run rebuild and diffing it against the sealed one. That is only honest if the limb's layer hierarchy is a pure, re-runnable function of recorded inputs — which is the hierarchy rule, and compaction is one of the two reasons it exists in the first place. `INTERACTIONS.md` records the shared projection this sits inside; what this design must guarantee is the narrower thing that composition is deterministic and its inputs recorded.

There is a bound worth stating because it simplifies the diff: a handover never crosses a limb boundary. Crossing is always a fresh session, so a successor is always in the same place as its predecessor, and the diff is therefore between two evaluations of the *same* limb's layers rather than between two places. That removes a case both designs would otherwise have to handle.

### Modular components, persistence, topology, operator lifecycle

Layer composition and configuration precedence are plausibly one piece of machinery; `PLAN.md` already flags the overlap and `INTERACTIONS.md` places construction and injection with modular-components. The scoping call is that **this experiment assumes the recursive-merge machinery rather than designing its own**, and contributes only what the config library cannot supply: the layer *set* and the precedence order, which are policy. That precedence order remains undesigned, as the What says.

Persistence-analytics holds limb configuration and reconnect state, and since a limb *is* a stored configuration row, persistence owns the row and this design owns what the columns mean. One relationship is worth naming so neither design confuses it: persistence proposes a project table keyed by host and root directory, and a limb row carries the same pair, but they are not the same thing — a project is a place on disk, a limb is a way of being in it, and a read-only limb and a full limb in one repository are two limbs in one project. A limb row therefore references a project rather than duplicating its identity.

Topology owns how bytes reach a remote limb, and operator-lifecycle owns making a compatible binary exist there. That leaves this design a precise remainder: everything after the binary exists and the connection is up — the limb's lifecycle, its self-termination on loneliness, its authority over its own environment, and the transparency claim that an agent launching a subagent in a remote place notices nothing. The version-compatibility gap the What names is therefore not a hole in this design; it is a handoff. Operator-lifecycle also assumes something from here and should be able to: detach works because a limb is a row in the brain rather than anything derived from the process's mode, so dropping a face does not change what the limb is.

### The empty and near-empty cells

Multi-client-ui and this design barely interact, as `INTERACTIONS.md` records. Both are about where things live, but one is about environments for agents and the other about views for humans, and they meet only through topology. Nothing here changes because a second face attached.

Oauth-credentials contributes only a restatement of invariant 1 — credentials never reach a limb — which is already an invariant and therefore not an interaction. It is worth one sentence only because it is what makes copying a binary onto somebody else's machine acceptable, and that is stated in the What already.

Cancellation-economics has nothing to say here. Layered-shutdown looks like a connection and mostly is not. (Its earlier claim of a cross-boundary "second form" of shutdown — far-end self-termination because kill authority stops at the network — was rejected by the user 2026-08-04: kill authority is exercised by command over the protocol, so a remote limb is shut down by being *told to*, with a budget, and kills its own process trees. This design's loneliness timeout is the fallback for a brain that vanished without commanding anything, not the remote shutdown path.) Layered-shutdown's one genuine contribution stands: a limb terminating on its orphan timer must reap its process trees on the way out, which the What records as a path nobody watches.

User-turn contributes a real constraint rather than an empty cell, though a small one: user tools execute through the limb even when the face and limb share a machine, which means an interactive editor over a *remote* limb has to work. That is a demand on latency and on the streaming path rather than on the limb model itself, but it is the case most likely to make the transparency claim in why #3 fail in practice, so it belongs in the same fixture as the remote path.

## Questions for review

- **Labelled provenance instead of "declared versus opaque".** I have proposed that limb context arrives as labelled blocks naming the layer that produced it, with truncation recorded as an event, and argued that this dissolves the limb-local-context-opacity open question because the brain always has the text anyway. That is my call, and it puts a real requirement on the limb protocol.
- **What columns does a limb row need?** `ssh_host` + `directory` cannot distinguish a read-only from a full limb in the same place, and describes the meta, service and pure-model kinds not at all, so kind has to be stored alongside the location. The notes leave the rest undecided — display name, resource limits, "which agent types are allowed to use it". Two calls in there are yours rather than mechanical: whether kind is stored as one of the six named types or as the three dimensions (where it runs, what it can do, how long it lives) held separately, and whether "which agent types may use this limb" is a property of the place at all or a policy that belongs on the agent side.
- **The factory needs a construction spec, and nothing supplies one.** A stored row says where a place is; making a place that does not exist yet needs a source repository, a ref, and whatever setup has to run before tools work. That is the factory's real content and it is absent from the notes. Is a per-project "how to manufacture a copy of this" spec something you want to write by hand, or should the factory derive what it can from the source limb (its git remote and current ref) and ask only about the setup steps?
- **Layer precedence is not designed and I have not designed it.** I have only bounded the problem — composition is a deterministic function evaluated at rebuild boundaries, and it plausibly shares machinery with modular-components' config work. The precedence order itself, and what happens when two layers contribute conflicting AGENTS.md-shaped instructions, is genuinely open. Is bounding it enough for now, or should this experiment be blocked until the layer design exists?
- **Who owns a manufactured limb's disk?** I propose the creating scope owns it and cleans up at scope completion, but only if the working copy is clean, with an explicit keep option and a report to the user otherwise. The notes have no position, and getting this wrong either leaks disk or destroys work.
- **Worktree as a materialisation option.** Much cheaper than a clone for the same-machine case, and it does give each place its own working tree, so it keeps the property that matters; what it shares is the object store and refs, leaving only ref contention and index locking as residual risk. Not in the notes; raised, not assumed, and decidable by measurement rather than by principle.
- **Remote gaps I could not fill.** Where the copied binary lives on the remote machine; how the remote platform and architecture are detected in order to send the right build; the reconnect timeout value; and what happens to a long-running command's output when the connection drops while the limb keeps running. The port-selection mechanism (limb prints its chosen port at startup, read over the existing SSH session) is my proposal.
- **Orphaned processes after a limb dies.** Ownership-based cleanup does not cover the case where the owner is gone, and the harness is not allowed to scan for strays. Container or namespace enforcement is your own hedged later idea; I have recorded the gap rather than filled it.
- **Naming.** The design's logic argues against *sandbox* and *runtime*, and against *context* on vocabulary-collision grounds. *Workspace* reads best in prose but collides with your own use of the word for a multi-repo checkout. Still your call; the two sentences any candidate has to survive are "a session exists with respect to one X" and "X-local context".
- **Is the brain-local config limb the meta limb?** `configuration-model.md` suggests user-level configuration might live in a brain-local limb, and the meta limb is an in-process limb that already provides config edits among its tools. If they are one thing, the open question about whether a brain-local config limb blurs the boundary is answered by something that already exists. If they are two, we have two in-process limbs and need a reason.
- **Where the factory is measured.** I have scoped it so this experiment measures *manufacture* — duration, observability, cleanup — while forked-subagents measures the *choice* between fork and a manufactured limb. That means neither experiment alone answers "what should parallel work do", which is the correct answer but worth confirming, since the factory only earns its keep if the other experiment concludes it is needed.
- **Labelled provenance is now load-bearing for a sibling.** I proposed it above as the answer to the limb-local-context-opacity question. Working the interactions showed it is also the left-hand side of context-updates' notice diff, which needs to know what version of what the context contains. So rejecting labelling costs more than this doc alone suggests.
