# Forked subagents — design scoping

Provisional; built stage by stage per `README.md` (why → what → interactions → summary). **Stages: why (user-involved) · what (agent-drafted, unreviewed) · interactions, summary — not yet done.** Derives from `source-notes/agent-hierarchy.md` (the spine), `source-notes/handoff-improvements.md`, and `source-notes/context-and-agent-loop.md`.

## Why

Seven roots, drilled back past the mechanisms the notes state to the situations — or the user's own desires — that actually drive them. Each is tagged with what it bottoms out in.

### 1. Pay for shared context once, not N times — *resource*

The note says fork is "good for KV cache reuse". The situation underneath: you've spent a whole session building context, and now you want three subagents on three parts of it. Fresh, each one re-reads everything you already paid for — three full-price passes over the same tokens. Forking makes the children share the parent's warm prefix, so the context is paid for once.

### 2. Decomposition keeps intermediate junk out of the parent — *resource (context)*

If the parent does everything itself, a hundred tool calls of intermediate junk sit in its context forever, bloating and dulling it. A subtask keeps that junk *inside the child*; only the task result and the important context come back. The parent stays small and sharp.

### 3. The user wants to see and run his own work as structured concurrency — *desire*

Not just for the agent — for the user. He wants to *work in this shape* (decompose, own, join) because it's how he wants to run work, and he wants a **map of his current work**: to see what's in flight and how it's structured.

### 4. Clean teardown at boundaries — *correctness + desire*

Work in flight has real side effects: files, commits, branches, external state. Hard-killing a line of work mid-action leaves a half-finished mess to untangle by hand. Structured ownership is what makes clean teardown *possible*: each task knows exactly what it owns, so it can be told to clean up and finish, unwinding only its own side effects. The desire underneath: **the user wants to change his mind about work and trust it unwinds itself cleanly, rather than leaving him the mess.**

This is not specific to cancellation. The same cleanup pattern runs at any boundary:

- **cancellation** — the involuntary case;
- **normal task/subtask completion** — return clean, not just return;
- **deliberate compaction at milestones** — tidy before handing the context forward.

### 5. Attachments make fresh siblings cheap — *resource*

If a task names a file to three parallel children, without attachments all three read it independently — three redundant reads of the same bytes. Attaching it once, executed in a shared init step, removes that. Note: a shared prefix already makes attachments largely redundant for *forked* children; the real usecase is *fresh siblings*.

### 6. Somewhere to keep working while subagents run — *desire*

Today, delegating stops the conversation — you wait. The user wants *somewhere to continue to record thoughts and do his own work while subagents do their thing* (the main-thread pattern: a user-facing child continues the workspace while autonomous siblings grind in parallel).

### 7. No manufactured obligation without consent — *safety/consent*

"An agent shan't manufacture an obligation for me without consent." An autonomous agent that could spawn a user-facing session would create a surprise blocking dependency on an absent human. So autonomous agents spawn only autonomous children; only user-facing agents (already in a consenting, blocking-on-user mode) may request user-facing ones.

## What

Almost everything in this design falls out of a single mechanism: **an agent blocks, and the act of blocking creates a scope containing its children.** There is no spawn-and-join, no background task registry, no global nursery. Once that is fixed, only three things are genuinely open — how a child's context is seeded, who is allowed to launch what, and how a task ends — and the rest of the sections below are the details of those three plus the tool surface that expresses them. The one part that is not a detail but a live risk is whether a forked child reliably stops at the slice it was given; that gets its own section, because if it does not work, the fork half of this design does not work.

### One primitive: blocking makes a scope

A scope comes into existence when a parent blocks, and it contains the children the parent blocked on. The parent does not continue until every agent in the scope has completed. There is no "launching into a child scope" as a separate operation: you either block — which creates a scope with children in it — or you launch a sibling into the scope you are already in. Any agent may launch a sibling, which means a parent can acquire a child it never asked for; that is intended, and it is the mechanism behind the main-thread pattern later.

Two visibility rules follow, and it is worth noticing that only one of them is a policy. Agents can see the *status* of their siblings but not their *results*, because results are only delivered to the parent when the scope completes — that is a deliberate rule, and it is invariant 6 restated. But the rule that an agent cannot see the status of its *children* is not a policy at all: a blocked parent has no turn in which to look. It is suspended. There is nothing to enforce, which is a good sign that the model is coherent rather than merely constrained.

The awkward consequence is that a scope's membership is not fixed at the moment it is created. Children can be added by siblings, and — see the user-facing section — by the user pressing a button. So the parent resumes with results from a set it did not fully choose. This has two concrete implications. Storage must represent a dynamic sibling set rather than a fixed child list captured at block time (`source-notes/agent-harness-design.md` already lists this under what storage must hold). And the resumed parent must be *told* what it is getting, in the resume framing itself, because it cannot infer the set from its own last turn. A parent that blocked on two children and wakes to four results, unannounced, is being handed a confusing context.

The notes raise, and do not settle, whether the shape is a tree or a DAG. The distinction worth drawing here is that **ownership** and **awaiting** need not be the same graph. Ownership must stay a tree — every task having exactly one owner is precisely what makes the teardown story in why #4 possible, since cleanup runs along ownership edges. Awaiting is where a DAG could appear: a task waiting on a sibling or a grand-sibling that is not its own child. The user leans toward requiring that such a target be *explicitly passed down* to be waited on, which reads naturally as capability passing — you can only await what your parent handed you. That keeps the wait graph legible and prevents an agent from inventing dependencies on work it has no business knowing about. It does not, by itself, prevent a cycle: a parent that hands A a handle to B and B a handle to A has constructed a deadlock. The notes contain no cycle rule, so this design does not have one either; it is listed as a question rather than papered over.

### The tool surface

Four tools matter, and all four are brain-native — provided by the brain regardless of which limb the session is bound to, alongside the other brain-owned tools like viewing session history. That placement is not incidental: launching a subagent means starting another agent loop, and the agent loop is the brain's (invariant 1).

**Task** takes the prompt for the child (`task`), which agent persona to use (`agent_type`), whether the session is user-facing or autonomous (`user_facing`), and which limb to run in (`context`). The `context` parameter is where fork-versus-fresh is decided, and the encoding is nicely economical: omitted or `"self"` means fork in the same limb; an explicit limb id or type means fresh in that limb, including something like `"global"` for a home-directory or no-project context; and naming the *same* limb explicitly means fresh in the same limb. So the parameter expresses a location, and the seeding mode falls out of whether that location is where you already are. The notes keep `user_facing` orthogonal to `agent_type` even though the two are informally conflated in practice — some personas are subagent-only, some user-facing-only — and that separation is worth keeping, because the launch rules in the user-facing section key off `user_facing`, not off persona.

**Resume** continues a previous agent session as a new subagent, taking the `id` returned by an earlier Task call (returned on success *or* error — a failed child is still resumable, which matters because "the child errored and I want to continue from where it got to" is the common case). Whether a session can be resumed as a *different* `agent_type` is open in the notes, with the interesting sub-question of whether the answer should depend on cache state: changing the persona rewrites the role framing, which is a rebuild-shaped change rather than an append-shaped one, so it may be free when the cache is already cold and expensive when it is warm.

Attachments are the fourth piece of surface, shared between Task and the compaction/handover tool, and they get their own section below.

The notes also float an **optional pre-step**: a temporary fork whose only job is to write a good task prompt, on the reasoning that what belongs in the prompt depends on the target agent type and context. It is explicitly an idea, not decided, and the stated tradeoff is that it adds latency and cost to *every* Task call. It reappears in the stopping section, because a well-written slice prompt is one of the few levers on the overrun problem.

### Seeding a child: fork, fresh, and the routing decision

Fork is the default: the child starts from a copy of the parent's conversation context, in the same limb, sharing the parent's warm prefix. Fresh is required when crossing a limb boundary — always, without exception, because a limb's instructions are load-bearing and you cannot append your way into a different environment (limb-model's why #1) — and fresh is also legitimate within the same limb, for instance when spinning out a meta or global session in the home directory context.

The routing decision therefore only exists inside one limb, and it is a *cost* judgement with a *quality* rider. The notes are explicit that the Task tool's prompt should make the parent act well as a router, and they enumerate the questions it should be asking: does the child need the same context as the parent — is this a natural continuation of what the parent was doing? Is the parent's context bloated, so that fresh would be cheaper anyway (with the note's own aside that it shouldn't be, because we hope the parent compacts before that happens)? Does the child need only *some* of the context? Does it need a different limb? Any yes to the last three pushes toward fresh.

Two more rulings shape the routing. "Fresh wins over forked-but-stale when the task is narrow/focused" — cheaper than a long-context cache miss if the new agent ends up needing less context. And the genuinely awkward case, a fresh subagent that wants forked siblings when the parent and all forks are already stale, is an open question in the notes with the position "tentatively lean toward fresh for narrow tasks". Both of those depend on predicting cache state, which is machinery this design shares with compaction and context-updates rather than owning.

There is a rider that the cost framing hides, and it is the reason the next two sections exist. Forking is cheap because the child inherits everything; the child inherits everything *including the parent's plan*, which is exactly what makes it prone to doing more than it was asked. Fresh is more expensive and structurally safer. So fork-versus-fresh is not purely an economic dial — it trades tokens against framing risk, and the experiment has to measure both sides or it will conclude the wrong thing.

### What a fork actually is, on the wire

This deserves separate treatment because the design's central cost claim rests on it and it is not yet proven.

A forked child is trying to be an **append-mode** agent: its context is the parent's context plus its instruction, so the provider's cache should hit on the shared prefix. `source-notes/context-and-agent-loop.md` flags the ambiguity precisely — a forked subagent is append-mode "possibly w.r.t the parent *as of the message before it sent the subagent tool call* - but that needs experimenting too." That "possibly" is doing real work, because there are several candidate encodings and they are not equivalent:

The child's transcript could begin at the parent's state *before* the Task call. This gives the cleanest prefix — every sibling shares an identical, already-cached history — but the child then has no idea it was launched. Its own instruction has to arrive as something appended after that point, and the child sees a conversation that ends mid-thought with a new instruction attached.

Alternatively the transcript could include the Task call itself, with the child's instruction arriving as the *result* of that call. This is more honest — the child can see it was delegated to, and by whom — but a tool call's result belongs to the caller's turn, so the child is reading a transcript in which it appears to have called Task on itself and been told what to do. Whether models handle that framing gracefully is unknown.

Or the parent's history could be replayed as a single seed block rather than as a live transcript, which removes the framing weirdness at the cost of losing exact prefix identity with the parent — and possibly with the siblings, depending on how the block is built.

The cache consequence differs per encoding, and so does the framing consequence, and the framing consequence feeds directly into stopping reliably. The notes are also clear that getting the provider caching right is a precondition rather than a detail: "we need to *very* correctly use OpenAI responses API & Anthropic messages API w.r.t. caching for this all to work." So the fork encoding is an experiment with two dependent variables measured at once — cache hit rate on the shared prefix, and behaviour of the child. Picking an encoding on cache grounds alone would be a mistake.

One design note that is mine rather than the notes': whichever encoding wins, the child's context must be reconstructible from the session record by any consumer (invariant 10 and invariant 3). A fork cannot be implemented as "the child holds a pointer to the parent's live context object", even when parent and child are in the same process, or introspection and rebuild both break.

### Stopping exactly where it was told to stop

This is the make-or-break question, and the notes state it more sharply than a paraphrase can: as to the model, "it appears it is given task A, then told to only focus on A.1, then told to only focus on A.1.3. But importantly, it must not continue on to complete A.1.4 or the full A.1. It must end its turn after A.1.3 - this must be reliable for forked agents to work well."

The reason this is hard is the reason forking is cheap. The child's context *is* the parent's context, so it contains the decomposition, the sibling tasks, and quite possibly the parent's own stated intention to complete all of A.1. Every one of those is evidence to the model that more work is expected of it. A fresh child has none of that evidence: it has its slice and nothing else, so overrun is structurally unlikely. Forking imports the plan and then asks the model to ignore most of it. Deep nesting makes it worse in the way the note implies — the framing has to survive being narrowed twice, and each narrowing is a smaller instruction sitting on a larger pile of context pointing elsewhere.

There are a handful of candidate mechanisms, all of which are proposals here rather than rulings:

*Recency and role.* The slice instruction arrives last and arrives in a role the model treats as authoritative for the current turn, rather than buried inside an assistant-authored plan. This is nearly free and is the obvious first thing to try.

*Ownership rather than prohibition.* Say "A.1.4 is not yours — another agent owns it" instead of "do not do A.1.4". This matches the model of the system: the sibling really does own it, and the child really will not see its result. Framing the boundary as a fact about the world rather than a rule imposed on the agent is more likely to survive, and it is honest, which usually helps.

*An explicit exit.* If ending a task requires calling a `done` tool, stopping becomes an affirmative act with a place to say what was accomplished, and turn end becomes observable rather than inferred. But the notes say autonomous sessions complete *automatically* at end of turn, and only user-facing sessions require a `/done` signal — while the cancellation flow says "please clean up then call done", which implies a `done` tool exists for at least that path. Those two statements need reconciling; it is listed as a question below rather than resolved by fiat.

*Prompt quality at launch.* The optional pre-step — a temp fork that writes the task prompt — is really a mitigation for this problem, and its cost/benefit should be judged here rather than in the abstract.

*Fallback rather than fix.* If forked children cannot be made to stop reliably, the design already contains its own escape route: fresh siblings with attachments, which get most of the token saving for the narrow-slice case without importing the plan. This is the strongest argument for building attachments as a first-class mechanism even though a shared prefix makes them largely redundant for forked children (why #5). It means a negative result on this experiment costs us the *default*, not the design.

What would make the result trustworthy is a task whose overrun is externally visible rather than judged by reading transcripts. A decomposition whose steps have distinguishable side effects — write file 3 and only file 3 — turns "did the child overrun" into an observation instead of an opinion, and lets the same fixture be run across fork and fresh, across nesting depths, and across framings, which is what makes the comparison mean anything. The harness cannot detect overrun in general, because knowing that A.1.4 was touched requires understanding what A.1.4 is; so the *measurement* has to be designed into the fixture rather than into the harness.

### Attachments and the shared seed context

Attachments exist because of a specific waste: a task that names a file to three parallel children makes three children read the same bytes. The agent calling Task can attach tool calls — file reads, skills, searches, maybe command output — which are sent to the child immediately on startup, appear as normal tool calls in its context, and crucially are executed once in a single shared "init" step across all parallel children. The note itself is tentative about the name (it writes these `"attachments" (??)`), and it lists the same mechanism on the compaction/handover tool, where the payoff is that the agent does not have to spend output tokens re-summarising a file it could simply hand forward. Preloading `agents.md` is called out as an obvious use.

The fresh-sibling launch has a matching trick for the *conversational* part. Rather than sending N independent fresh children, you start one child with only the shared context and tell it to wait for further instructions. That first API request establishes the shared cache; the differing instructions then go to the different branches, all of which share the cached prefix. So there are three launch paths in total, and they line up neatly: forked Task, where the parent's own context is the shared seed; fresh Task, where a deliberately constructed seed plus attachments is established by an initial request and then branched; and the compaction/handover tool, which has the same shape as the fresh variant — context, attachments, and a task.

The two-part launch idea belongs here too. The agent calls the tool; it receives a *user message* rather than a tool result, containing instructions on how to use the tool correctly; it calls again to confirm. The notes judge this worth it for handover, "probably not" for subagents — but with a specific hedge worth keeping: "However we could still try it, as it might give us a good cache point for diverging the parent agent into forked subagents." That is a real technical argument, not just diligence: the confirm step is a deterministic boundary in the parent's context, which is exactly what you want to fork from.

### What comes back

A result is the last message part in a turn. What is *in* it is determined by prompting, and ideally it is "what the parent needs to know." Failure counts as completion with an error result, and whether one child failing aborts the whole scope or merely propagates an error to the parent is called out in the notes as needing experimenting.

Two things follow. First, because the result is the *only* thing that crosses back — the parent never sees intermediate content, by design, since that is the whole point of why #2 — the quality of the result is load-bearing in the same way handover quality is load-bearing. The same class of failure (a summary that drops the thing that mattered) has the same cost, and this design does not get to assume good results any more than compaction does.

Second, invariant 9's four-valued outcome (ok / error / cancelled / panicked) has to appear here, because a parent resuming needs to know *which* of those it is looking at, and the last-message-part definition alone does not say. Cancelled is the interesting case and it resolves cleanly: a cancelled child is asked to clean up and finish, so it has a final turn, so it has a last message part — a cancelled child returns a real result describing what it did and what it left behind. Panicked is the one that cannot, which means the outcome class has to travel alongside the result rather than being encoded in it, and the parent framing has to be able to say "this child died without a result".

### Ending a task: one procedure, three reasons

Why #4 makes the case that cleanup is not a cancellation feature; it is what ending a task means. So the design should have a single finish procedure, parameterised by the reason it is running: cancellation (the involuntary case), normal completion (return clean, not just return), and deliberate compaction at a milestone (tidy before handing forward). The mechanics are the same — the agent is told the task is ending, it is allowed to do work to leave its own side effects in a good state, and then it produces its final message. Only the framing text and the outcome class differ. Building three separate paths for this would be the mistake.

Cancellation is the case with real mechanics, and the notes are specific about all of them. Cancellation is a **message** — "your task has been cancelled, please clean up then call done" — not a kill. It completes **upward**: children clean up and finish first, then the parent, because a parent cannot tidy correctly until its children have; whether a message also travels on the *downward* pass, or whether the downward pass is purely a control fact that reaches the leaves without being shown to any model, is explicitly TBC. It is **soft by design**, which means it keeps burning tokens on purpose, because cleanup is the point — with a hard stop available later as a backstop. And forked children need care: each cleans up only *its own* subtask's side effects, not shared parent state, which is a genuinely difficult instruction to give a child whose context is the parent's context and which therefore knows about all of it.

That leaves a tension with invariant 9 worth naming, because it looks like a contradiction and I think it is not. Invariant 9 says a drain structurally cannot start new work; soft cancellation deliberately starts new work, in the form of cleanup tool calls. The reading that makes both true is that these are two different layers. Agent-level cancellation is a *new instruction* to a still-running agent: the loop continues, requests are still made, tool calls still execute, and the turn ends when the agent says it is done. The drain is what runs *after* that, at the level of the harness's own in-flight work, and that is where "cannot start new work" applies. If that reading is right, the two are consistent and the vocabulary should distinguish them; if it is wrong, one of the two needs to change. It is flagged below because it is my reading, not a ruling.

Soft cancellation also needs a bound, since an agent asked to clean up can decline to finish, and the cost is real money. The mechanisms available are already recorded elsewhere in the project: a parent-held timeout backstop with a descending deadline budget (the layered-shutdown pattern), and the hard stop the notes name as a later backstop. The interaction between "cleanup deliberately spends tokens" and "how many tokens is that, actually" is the cancellation-economics question, which is why that small experiment matters to this one.

### The user-facing half

An agent session is either user-facing or autonomous, and the difference shows up in exactly two places. Completion: an autonomous session completes automatically at end of turn, while a user-facing one completes when the user signals `/done`, after which the agent writes its response. Launch: an autonomous session can be launched freely by any agent, while a user-facing one requires the user's permission and can only be *requested* by an agent that is itself user-facing. That last rule is why #7 made concrete — an autonomous agent cannot manufacture a blocking dependency on an absent human, because it cannot ask for one. A user-facing agent is already in a mode where blocking on user input is expected, so a request is just another form of that. The notes offer an escape hatch: permission requests could expire after a timeout, so even a user-facing agent's request does not block indefinitely if the user is absent. Not decided.

There is a wording collision here that should be resolved deliberately. `REQUIREMENTS.md` says permission prompts and approval theatre are explicitly unwanted, while this design says launching a user-facing session "requires user permission". I think these are compatible because they are about different things: the harness is not asking permission to *act* — it is asking for the user's *attention*, which only the user can grant, and which the user is entirely free to ignore. Framing it as an invitation rather than an authorisation prompt keeps both positions intact, and makes the expiry idea natural rather than an escape hatch. Recorded below as my call.

Multiple user-facing sessions are supported and appear in a session switcher, and the user has a button to launch a user-facing session into a scope that does not currently have one. That button is worth pausing on: it means scope membership can change with no model involvement at all, from outside the hierarchy. It is the same primitive as an agent launching a sibling, exercised by the user, and it reinforces that dynamic sibling sets are a first-class case rather than an oddity.

The **main-thread pattern** is what all of this is for. A parent that wants to keep talking to the user while parallel work happens forks a user-facing child — from the user's point of view the conversation simply continues, with no seam — and also launches one or more autonomous siblings into the same scope. The interactive part runs in the child; the grind runs in the siblings. The user calls `/done` when satisfied and the user-facing child completes; the autonomous siblings may still be running, and the scope completes only when all of them are done. The parent then resumes with all the results, having seen none of the intermediate content.

Two open threads sit here. The user-facing child is still a subtask, so it returns only a summary to its parent — and how that is surfaced to the user effectively is an open UX question, because the user has just had a whole conversation whose visible outcome is a summary handed to an agent he cannot see. And it is unsure what powers a user-facing sibling gets over its siblings; whether it can send them messages, for instance. On that second one there is a shape worth considering rather than adding a new mechanism: the notes elsewhere observe that you can start a subagent whose role is orchestrating the other subagents, and that this "may become the default". Supervision is already expressible as *parenthood*. If a user-facing session should be able to direct workers, the cleanest answer is that the workers are its children rather than its siblings — which costs the main-thread arrangement, since children of the user-facing session are not siblings of it. That is a real choice between two shapes, not a detail, and the user's stated position is only "unsure".

Names are the last user-facing piece, and they exist for why #3 — the map of work. They are auto-generated, short and descriptive, and they lengthen with nesting naturally, as in `tk-prodsync-findfiles` and then `tk-prodsync-findfiles-refactor-imports`. The user can edit a name when spinning out a user-facing scope, and a main-thread child inherits the parent's name with a suffix such as `'` or `*` — not yet decided which. The notes do not say *what* generates the name, and it matters a little: a model-generated name costs a call or an output field on Task, while a derived name is free but worse. That gap is real and is listed below rather than filled in.

The stuck-child case belongs here too. A forgotten `/done` or a hung child blocks the parent's scope indefinitely. The notes treat this as intentional — the user is in charge — with the permission prompt that precedes it named as a known UX pain point, and expiry noted but not decided. The design consequence is that stuck scopes must be *visible*: a blocked parent and the reason it is blocked are exactly the sort of thing the analytics surface should be able to answer, which is why "stuck scopes" appears in the persistence requirements.

### The unresolved one: siblings sharing a filesystem

Fork-by-default means same limb by definition, and same limb means the same filesystem. So the default way to launch parallel children is also the way to put several agents into one working directory at once, and the notes are blunt that experience with that is poor. This is not resolved. The two directions recorded are clear instructions and context telling forked agents what scope of the workspace they own, and "Some kind of borrow-checker-style rule on mutable workspace regions (tentative, not designed)". Neither is designed, and I am not going to invent one here.

What can be said is where the difficulty actually lies, because it is sharper than "concurrency is hard". The cheapest thing (fork, sharing a warm prefix) and the safest thing (separate working copies) point in opposite directions, and the design already contains the safe option: the limb factory can produce a fresh clone per child (limb-model's why #4). But crossing into a new limb forces a fresh context, so taking the safe option costs exactly the cache saving that motivated forking. That is the crux. It suggests — and this is analysis, not a ruling — that fork's natural home may be *sequential* decomposition and *read-mostly* parallel work, with write-heavy parallel work running as fresh siblings in freshly-made limbs plus attachments. If that turns out to be right, "fork by default" remains true for the common case while the headline parallel-work case is mostly fresh, which is a different emphasis than the notes currently carry. It is raised as a question below rather than treated as settled, since it touches why #1.

The instruction-based direction has one property worth noting in its favour: it is the only one that costs nothing to try, and it composes with the ownership framing already needed for stopping reliably. "A.1.4 is not yours" and "`src/parser/` is not yours" are the same sentence. If ownership framing works well enough for one, it is worth measuring for the other.

### The considered alternative: task calls as code

The notes float a different shape for all of this, and the user's own verdict on it is "Well, that's complicated but we can certainly consider it." The shape: create at most one shared "seed context" per limb, containing context and attachments; create subagents in a limb by attaching a task to that context; your own context is always available, so that is how you make forked agents; await on all subagents, or have them await each other before starting by attaching their outputs to each others' tasks; and finally return a response, typically just the array of all subagent results.

It is worth taking seriously because it collapses several separate mechanisms into one vocabulary. The shared seed context stops being a hidden optimisation inside the fresh-launch path and becomes a named, reusable thing. Fork and fresh stop being a mode flag and become a choice of which context you attach a task to — your own, or a constructed one. Most interestingly, sibling-to-sibling dependencies become explicit data flow: "have them await each other by attaching their outputs to each others' tasks" *is* the explicit passing-down that the user leans toward for the DAG question. So this alternative is not orthogonal to the tree-versus-DAG thread — it is where that thread naturally lives.

What it costs is that the model now writes a small program, and every mistake it makes is a program bug rather than a wrong tool argument. The error surface grows, the failure modes get less legible, and — most relevant to this experiment — stopping reliably gets harder to reason about, because a child's task is now assembled by code rather than stated in a prompt whose framing we control. It also makes the tool surface much larger than "Task plus Resume", which cuts against the thinness the rest of the design has.

The honest position is that the two shapes are not mutually exclusive on a timeline: the parameter-based Task tool is testable now and is what the experiment should use, and if the seed-context-and-attach vocabulary is needed, it is a strictly later, richer surface over the same underlying primitives. The hedge stays the user's.

### Putting it back together

The design is one primitive with three variables around it. Blocking makes a scope; the scope is the unit of ownership, cleanup, and visibility, and it is a tree because cleanup runs along ownership edges. The first variable is how a child's context is seeded — fork for continuity and cache, fresh for narrowness and for any limb change — and this is the only place where cost and framing genuinely trade against each other. The second is who may launch what, which is a two-value rule (user-facing agents may request user-facing children; nobody else may) carrying the consent property from why #7. The third is how a task ends, which is one procedure with three reasons, of which cancellation is the interesting one: a message rather than a kill, completing upward, deliberately spending tokens because the cleanup is the point. The tool surface stays thin — Task, Resume, attachments, and the brain-native status and history tools — and the result that crosses back is the last message part plus an outcome class.

The thesis this design asserts, and that the experiment has to test, is that structured concurrency with forked context is both *usable* by the model and *cheap*: that a child can be given a slice of a plan it can see all of and reliably do only that slice, and that forking really does buy the cache saving it promises. It would be falsified by any of: forked children overrunning their slice at a rate that makes decomposition unreliable, with no framing that fixes it; forked children failing to hit the shared prefix in practice, which makes fork no cheaper than fresh; parallel siblings in one limb corrupting each other's work often enough that fresh-plus-clone becomes the only safe parallel path; or the hierarchy being formally clean but illegible to the user, which fails why #3 regardless of the mechanics.

It touches invariant 6 head-on (parents block, sibling results stay hidden), invariant 9 (cancellation as message, four-valued outcomes, the drain reading above), invariant 2 (a Task call continues a tool loop and therefore legitimately triggers requests; a sibling status change explicitly does not), invariant 3 (sibling status is a projection for the model, the work map a projection for the user), invariant 5 (blocked parents, dynamic sibling sets, resume targets and stuck scopes all have to be durable and queryable), invariant 10 (a forked child's context travels as data, not as a reference to the parent's live state), and invariant 1 (every child's loop runs in the brain).
