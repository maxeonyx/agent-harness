# Multi-client UI state — design scoping

Provisional; built stage by stage per `README.md` (why → what → interactions → summary). **Stages: the throbber's purpose (user-involved, confirmed 2026-08-04) · why, the rest of the what, interactions, summary (agent-drafted, unreviewed).** Derives from the multi-client and GUI passages of `source-notes/tech.md`, plus `source-notes/tui-styling.md` and `source-notes/throbber-design.md` for the UI content that attaches here.

Before this experiment, prototypes use an append-only CLI. After it, a real reactive TUI and a real web GUI share one underlying client state model.

## Summary

The motivating story is one person changing where he is standing, not two people collaborating: "I should be able to seamlessly transition between my phone (web app?) and a TUI on my desktop", with the work continuing across the handover. That sets the bar at *continuity* rather than at concurrent editing — concurrent use is in scope, and sizing it as the rarer case is a judgement of mine rather than something the notes settle — and it makes the worst available failure concrete. A phone that has been asleep with an old draft in its buffer reconnects and pushes that draft over something newer; nothing warns anyone, and typed text is gone. Silent loss is worse than a visible error because there is no signal to react to.

The design's engine is a classification, and one question assigns state to it: *what breaks if a second client does not know this?* Nothing breaks for **face-local** state — scroll position, which pane has focus, viewport size and everything derived from it — and two clients on different screens actively want different values, so it stays where it is. Something does break for **shared-live** state: the user picks up his phone and the session is not where he left it. That class is draft contents and the cursor within them, which files are open and edited but unsaved, which user tool is open and enough of its live state to render the same thing, and undismissed notifications — all of it authored by the user and not yet finished, which is both why it is his to lose and why the model must not read it. **Durable** state is what the session record is made of, and this design adds nothing to it except the requirement that shared-live state has a durable counterpart wherever the *fact* of an action matters. What the harness is currently waiting on looks like a fourth class and is not one: it is a view any caught-up client can *derive* from facts the record already carries, so it is stored nowhere.

Two things about that classification are worth noticing. Shared-live turns out to be a handful of things rather than an entire UI, because user-turn routes file access through the limb even when face and limb share a machine, which leaves the editing buffer as the only file state on the face's side. And the same subject usually yields two events in two classes: that the user opened this file, looked at these regions and made this edit is a finished fact, while the file being open in the second pane with the cursor on line 240 and an unwritten edit in the buffer is live state. The test between them is whether the thing has stopped changing.

The negative half of the design matters as much as the positive half: shared-live state must never be projected to the model, because an agent reading half-typed thoughts and abandoned phrasings as though they were instructions is easy to arrive at by accident and expensive to get wrong. Stated as a rule it survives until someone adds a convenient field, so it is made structural instead, and invariant 3 already supplies the structure: projection is *selection*, and the model-facing projection selects context facts, so shared-live state is a class it never names. A flag on a row is a thing someone forgets; a projection whose domain does not contain the type is not. That needs no second store — where the events physically live is a separate question with separate reasons. The check is a black-box test at the wire: type a long draft, open a file, run a search, send none of it, cause a request by other means, and assert the request contains not one character of any of it. `/dump` is the other surface, with one subtlety that is easy to get backwards — shared-live state appearing in a dump is not the violation, since `/dump` deliberately shows what the model cannot see; appearing there *unmarked* is.

Making a stale send recognisable needs no new machinery here. A send carries the highest sequence its client had observed for the state it is modifying, so "this arrived from a client that had not seen X" becomes a representable fact rather than an indistinguishable write. That mechanism is topology's, which needs it for cancellation across role boundaries whether or not the UI case exists, and this design inherits it. What this design owns is the policy. Invariant 7 supplies half of it — "stale clients cannot silently overwrite newer state" settles who may win — and runs out on the other half, since "the user wins on conflicting edits" has no content when both sides are the user. So one clause is added: no branch of the user's own text is ever discarded silently either, and a stale send may be rejected, merged or superseded provided the losing text stays recoverable and the divergence is visible. Silently dropping the phone's draft is exactly as silent as silently overwriting the desktop's, and the invariant only forbids the second. Reconnect is otherwise deliberately ordinary: a face keeps its own replica and a resume point and replays from there, and client-assigned send identities make at-least-once delivery harmless. The sharp requirement is that a freshly attached face must render a correct, complete view from catch-up alone, with no privileged access and no separate bootstrap path — which is what makes the throbber load-bearing rather than decorative, since three of its four states are already derivable and the fourth, harness internals, is recorded nowhere and so forces internal operations to emit start and end facts.

The genuinely unresolved part is how a shared draft buffer converges, and the shape of the problem is smaller than it first looks: a session-authoritative brain already exists, so general peer-to-peer convergence is not needed, and the common case is sequential handover — concurrent use is in scope, but sizing it as the rarer case is a judgement here rather than a ruling in the notes. What remains hard is local echo — the client being typed into must show the character immediately and must not visibly jump or lose the cursor when the server's ordering disagrees with its local guess. Three candidates ascend in cost: causal last-writer-wins with visible rejection; server-ordered operations with client-side rebase; and a CRDT text type, whose main purchase is a coordinator-free convergence this architecture does not need, so it should be chosen on the strength of the typing experience rather than of the convergence guarantee. The second and third are reachable from the first without rewriting the state model, provided sends carry causal position from the beginning — so the experiment builds the cheapest, uses it across two devices as the user actually would, and finds out whether it is annoying. The exit condition is two client *instances* on one session — which is a fixture topology needs anyway — plus one headless client that asserts it can derive the whole view from catch-up, since two instances prove the state model and the headless consumer proves the model is not shaped around a terminal. A web GUI is a consumer of the proven model rather than part of the proof. Falsification is correspondingly concrete — any part of the view a freshly attached client cannot derive from catch-up, a stale send either silently overwriting newer state or silently discarded, a reconnect that duplicates or drops input, any character of shared-live state on the wire or unmarked in `/dump`, face-local state that turns out to need replicating, or a second consumer that only works by adding state paths the first one did not need.

## Why

### 1. The user wants to move between devices mid-work — *desire*

Stated directly: "I should be able to seamlessly transition between my phone (web app?) and a TUI on my desktop." The GUI should be usable as a web app and not only as a desktop app. This is the motivating story — not two people collaborating, but one person changing where he is standing while the work continues.

That framing matters because it sets the bar at *continuity* rather than at concurrent editing. The common case is sequential handover between the user's own clients.

How much weight simultaneous use carries is a **sizing judgement I have made and the notes do not settle**, and it should be visible as one, because the cheapest convergence mechanism below is only defensible if the judgement holds. The notes do also ask for concurrency directly — "Our communication should be good enough to support multiple clients on the same session" — and `REQUIREMENTS.md` states the stakeholder need concurrently: "multiple faces share live UI state (drafts, open files, panes)". What tips it is the transition story being the one with a scene attached, plus the user's own "Mostly for the live state though" qualification on the CRDT idea. So: both are in scope, and I have sized simultaneous editing as the rarer case. If that is wrong, the convergence choice changes and little else does.

### 2. Losing the user's work silently is the worst failure available — *correctness*

Invariant 7: stale clients cannot silently overwrite newer state, and the user wins on conflicting edits. The story is a phone that has been asleep with an old draft in its buffer, reconnecting and pushing that draft over something newer. Nothing warns anyone, and typed text is gone.

Silent loss is worse than a visible error because there is no signal to react to. So stale sends must be *representable* — the model has to be able to say "this arrived from a client that had not seen X yet" and act on that fact, rather than applying writes in arrival order.

### 3. Some UI state is genuinely shared and editable, which is the hard part — *correctness*

Draft buffers and file open/edit state are the difficult case: they are edited by the user, live, from possibly more than one place. The notes suggest CRDTs for the draft buffer, with the mechanism explicitly exploratory, and offer the observation that an event-based architecture is already most of the way there — "By being event based, we are essentially implementing CRDTs, and that's OK. Mostly for the live state though - as we do have a session-authoritative brain server."

That last clause is the useful constraint. There is an authoritative server, so this is not peer-to-peer convergence in the general case; it is convergence of live state under a sequencer that already exists.

### 4. Shared UI state must not become model context by accident — *correctness*

This one is easy to overlook and expensive to get wrong. Draft buffers, cursor positions and open-pane state exist for the human. If they leaked into the model's context, the agent would be reading half-typed thoughts and abandoned phrasings as though they were instructions.

This is invariant 3 applied here — an event is about its emitter, and consumers project it — but the specific requirement is a *negative* one: there must be a class of state that is shared between faces and explicitly never projected to the model. Note the deliberate tension with user-turn, which exists precisely to give the agent visibility into user activity. The line between them needs drawing exactly: what the user *did* is context; what the user is *in the middle of typing* is not.

### 5. Not everything should be shared — *resource/correctness*

Face-local state stays face-local. Scroll position, focus, transient visual state: replicating it would be both wasteful and wrong, since two clients on different screen sizes do not want the same view. So the model needs at least three classes — face-local, shared-live, and durable — which lines up with the lifecycle classes invariant 5 demands of storage.

### On sequencing

Whether this is its own experiment, and whether it runs before the reactive TUI is built, is a sequencing question rather than a why. It lives in `PLAN.md`, which owns the pool and its ordering.

## Forward: what these roots force

- **An explicit taxonomy of client state** — face-local, shared-live, durable — with every piece of UI state assigned, and a rule that shared-live is never projected to the model.
- **Causal representation of client sends.** From #2: a send carries what the client had seen, so a stale send is a recognisable fact rather than an indistinguishable write. This is the same causal-consistency machinery topology needs, applied to faces.
- **Reconnect and catch-up without duplicates**, which means an ordered durable event stream and a per-client resume point — again shared with topology.
- **A convergence mechanism for the draft buffer**, chosen empirically. CRDT is the named candidate; the event log plus an authoritative server may be sufficient. This is the experiment's central open question.
- **Two clients, and one of them not a TUI.** The exit condition has two halves that are cheap to conflate. Everything the state model claims — replication of shared-live state, catch-up-only rendering, stale-send detection, draft convergence — needs two client *instances*, not two renderers, and two TUIs on one session test all of it. What a second renderer additionally proves is only that the model is not accidentally TUI-shaped, and a headless client that asserts it can derive the whole view from catch-up proves that at a fraction of the cost of a web GUI.
- **UI content belongs in the soft middle.** Self-modification's boundary puts "pretty much all UI content — even the TUI content" in the rapidly-iterable layer, with only the rendering framework in the shell. So this experiment should produce UI *content* that is replaceable without recompiling, which is a constraint on how the state model is exposed.

## What

Everything here follows from one decision: which class a given piece of state belongs to. So the state classes come first, then the awkward cases that seem to belong to two classes at once, then what a client's send has to carry for staleness to be a fact rather than an accident, then reconnect, then the genuinely unresolved part — how a shared draft buffer converges. The negative requirement gets its own treatment because a rule nobody can violate is better than a rule everybody agrees with. The UI content comes last and is deliberately subordinate, though one piece of it turns out to be a good test of the state model.

### Three classes, and the question that assigns state to them

The three classes are face-local, shared-live, and durable, and they line up with the lifecycle classes invariant 5 already demands of storage. Assigning state to them is easier with one question in hand: *what breaks if a second client does not know this?*

Nothing breaks for **face-local** state, so it stays where it is. Scroll position, which pane has focus, viewport size and everything derived from it, the currently visible slice of a long transcript, selection highlighting, whether a collapsible block is expanded *on this screen*, key-mode state, in-flight animation phase. Two clients on different screen sizes actively do not want the same values for these; replicating them would be both wasteful and wrong. This is also the class that makes invariant 10 relevant to faces, since a face is not entitled to assume anything about another face's screen.

Something does break for **shared-live** state: the user picks up his phone and the session is not where he left it. Draft buffer contents, and the cursor position within them, since resuming typing on another device with the cursor somewhere arbitrary is worse than useless. Which files are open and what has been edited in them but not yet saved. Which user tool is currently open — the terminal, the file explorer, the search — and enough of its live state that the other client can render the same thing. Notifications not yet dismissed. This is the class why #3 calls the hard part, and it is small, which is worth noticing: shared-live state is a handful of things, not an entire UI. The common thread is that all of it is *authored by the user and not yet finished* — which is why it is his to lose and why the model must not read it.

**Durable** state is what the session record is made of, and this design contributes nothing new to it except the requirement that shared-live state has a durable counterpart where the *fact* of an action matters: the user opened this file at this point in the session, ran this command, searched for this. Persistence-analytics owns how any of that is stored.

One thing that looks like a fourth class is not one. "What the harness is currently waiting on" has to be visible to every client, and a freshly attached face has to get it right, so it is tempting to file it as shared-live. But it is not state anyone holds — it is a **view derived** from durable facts the session record already carries: a request was sent, a response began, a tool call started or exited, the turn is waiting on the user. Any client that has caught up can compute it. Filing it as a class of its own would put a derived value in a store, which is the mistake the classification exists to prevent; the throbber section below deals with the one part of it that genuinely is not yet recorded.

The classification is not decoration. It decides what crosses a face boundary, what survives a disconnect, and — most importantly — what may ever reach the model.

### The same datum in two classes: what the user did versus what he is doing

The interesting cases are the ones that look like they belong to two classes, and there is a clean line through them, offered here as a proposal that answers the first open question below rather than as something the notes settle.

A file the user has open produces two different things. There is a fact: at this point in the session the user opened `src/limb.rs`, looked at these regions, and made this edit. That fact is durable, it is projected to the model, and it is exactly what user-turn exists to provide — the agent gets to see what the user is doing without being told. And there is live state: the file is open in the second pane, the cursor is on line 240, three regions are expanded, and the buffer holds an edit that has not been written. That is shared-live, so the phone can render the same view, and it is never projected to the model.

So: same subject, two events, two classes. What the user *did* is context. What the user is *in the middle of doing* is not. The test that distinguishes them is whether the thing has finished being true — a fact does not change again, while live state changes on every keystroke. That also explains why the draft buffer has no durable counterpart until it is sent: an unsent draft is not something the user did.

### A send is a proposal with a causal position

Invariant 7 requires that stale clients cannot silently overwrite newer state, and the story behind it is a phone that has been asleep with an old draft, reconnecting and pushing that draft over something newer. Arrival order cannot detect that, so a send has to carry where the sending client *was*: the highest sequence it had observed for the state it is modifying. Then a stale send is a representable fact — "this arrived from a client that had not seen X yet" — which is precisely what the notes ask for. It is the same causal machinery topology needs across role boundaries, applied to faces, and it is why the send is a *proposal* until the brain sequences it into a fact.

Invariant 7 then decides half of what happens next, and it is worth reading both of its clauses because they do different work. "Stale clients cannot silently overwrite newer state" is exactly this case and settles it: the sleeping phone may not win by arriving. "The user wins on conflicting edits" is the clause that runs out, because it resolves user-versus-agent and both sides here are the user — the phone's draft and the desktop's newer draft were both typed by him, so there is no "the user" to pick.

What the invariant leaves open is therefore the losing branch, and that is where this design adds one clause: no branch of the user's own text is ever discarded silently either. A stale send may be rejected, merged, or superseded, but the losing text has to remain recoverable and the divergence has to be visible. Why #2's root is that silent loss is worse than a visible error because there is no signal to react to — and silently dropping the phone's draft is exactly as silent as silently overwriting the desktop's. Both failures are the same failure, and the invariant only forbids one of them.

### Reconnect: what the face keeps and what it re-derives

A face holds its own replica of the state it renders, rather than treating the brain's memory as a query surface, and it keeps a resume point — the highest sequence it has consumed. Reconnecting replays from there, and duplicates are prevented the ordinary way: every client-originated send carries a client-assigned identity, so replaying a send that was already sequenced is recognised and dropped rather than applied twice. Delivery can then be at-least-once without consequence, which is what lets the transport underneath stay simple.

The parts of this that are shared machinery with topology — the ordered stream, the resume point, the handshake in which a joining peer declares itself, catches up and signals ready — belong to topology's design and are not restated here. What belongs here is the consequence for the UI: a face that has just attached must be able to render a correct, complete view from catch-up alone, with no privileged access and no separate bootstrap path. If any part of the view can only be obtained by having been present when it happened, that part of the state model is wrong.

### Converging the draft buffer

This is the experiment's central open question and the notes are deliberately exploratory about it, so what follows is an argument about the shape of the problem rather than a choice of mechanism.

Two observations from the notes constrain it. The first: "By being event based, we are essentially implementing CRDTs, and that's OK. Mostly for the live state though - as we do have a session-authoritative brain server." The second is why #1's framing — the motivating story is one person moving between his own devices, so the common case is *sequential handover*, and simultaneous editing is possible but secondary.

Together those change what the hard part is. Convergence in the general, peer-to-peer sense is not the problem, because a sequencer exists and can order operations. What remains hard is local echo: the client that is being typed into must show the character immediately, and must not visibly jump or lose the cursor when the server's ordering disagrees with the local guess. That is an intention-preservation problem, and it is the reason text editing is harder than it looks even with an authoritative server.

Three candidate mechanisms, in ascending cost. **Causal last-writer-wins with visible rejection**: sends carry their causal position, a stale one is refused, the client is shown the newer state and its own text is preserved somewhere it can be recovered from. Cheap, obviously correct, and slightly rude in the rare simultaneous case. **Server-ordered operations with client-side rebase**: the client applies locally and optimistically, the brain assigns the order, and the client rebases its unacknowledged operations onto the sequenced ones — which is what a central-server editor does, and what the event log plus an authoritative brain almost already is. **A CRDT text type**: convergence without a coordinator, at the cost of per-character metadata and a harder debugging story. The honest observation is that the third buys peer-to-peer convergence, which the session-authoritative brain means we do not need; that is not an argument against it, but it is an argument that it should be chosen on the strength of the typing experience rather than on the strength of the convergence guarantee.

The experiment's job is to build the cheapest one, use it across two devices as the user actually would, and find out whether it is annoying. That ordering matters: the second and third are both reachable from the first without rewriting the state model, provided sends carry causal position from the beginning.

### The negative requirement, made structural

Shared-live state must never be projected to the model. A rule stated that way survives until someone adds a convenient field, so the design should make the violation impossible rather than discouraged.

Invariant 3 already supplies the mechanism, and it is cheaper than a second store. Projection is where a consumer *selects* the events it cares about, and the model-facing projection selects context facts. Shared-live state is a distinct event class, so the model projection simply never names it — and a projection that cannot name a type has no path to it, enforced by the type system rather than by anyone remembering. That is the absent path, obtained without leaving the one-stream-many-projections model that everything else here relies on.

The distinction worth holding onto is between a *flag* and a *class*. A flag says "this row exists in the model's input, don't include it", and someone eventually forgets. A class says the model's projection is a function whose domain does not contain this, which is not a thing to forget. Where those events are physically stored is then a separate question with separate reasons, and persistence answers it below.

`/dump` then becomes the surface where this is checked, though with one subtlety worth stating because it is easy to get backwards. `/dump` deliberately shows everything the model *cannot* see, marked as such, so shared-live state appearing in a dump is not itself a violation — appearing there *unmarked*, or appearing on the wire at all, is. The test is a black-box test at the wire: type a long draft, open a file, run a search, send none of it, trigger a request by other means, and assert that the provider request contains not one character of any of it, and that anything about it in the dump is marked invisible. The deliberate tension with user-turn is resolved by the fact/live-state line above — user-turn's projections carry what the user *did*, and there is nothing in this class for them to reach.

### The UI content that attaches here

This material is subordinate to the state model — it is what gets rendered once the model is settled, and per self-modification's boundary almost all of it is soft middle rather than shell, since only the rendering framework belongs in the compiled shell. It is recorded here because this is the experiment where the front-ends first become real.

The TUI takes OpenCode's TUI as its reference — "See OpenCode's TUI, basically ... I think we should liberally take from opencode" — with an Anthropic-web colour scheme rather than OpenCode's: Anthropic beige background, off-white inactive editable areas, white active ones, mostly black text, important text a dark maroon, with the actual Anthropic web colours as the reference. The geometric principle is that 1 row of height equals 2 columns of width, everywhere, and where a colour transition pads an element we use half-block transitions to increase density — effectively half a row of padding shared by the elements above and below, and since half a row is one column, containers with half-row padding above and below get one column of padding left and right. opentui-rust is the intended library. Its scrollbar primitive is close: "I like it a LOT but it's not quite perfect. It needs configurable *half block end caps*" — the scrollbar optionally extending by an additional half block into the space where arrows would be, so it fits the styling. That is a change to somebody else's primitive, and the notes do not say whether it is a fork or an upstream contribution. All of this is already captured in the user's OpenCode fork UI compactness change, which makes it a port rather than a design. One item is explicitly unachieved rather than merely unbuilt: "I would like to have windows-style persistent select, right click to copy, right click to paste. I never got that working in opencode."

The throbber is the piece that is not merely decorative, and it is worth putting slightly ahead of the rest. The design is to show what the harness is *waiting on* rather than generic motion, across what the notes count as four things: a model response, split into the request having been sent but not yet started and the model actively streaming; a tool call executing; harness internals, meaning things like an MCP service initialising, a tool result being processed, internal reconciliation, reordering conversation history, or any other internal compute; and user input, which "I don't think we have a throbber" for — "probably some kind of state where the throbber is not actually moving ... either a different state entirely, or perhaps a very slow throbber".

That makes the throbber a demanding test of the state model rather than a decoration: a face that has just attached must render the correct waiting-state immediately from catch-up alone, with nothing held in brain-internal memory. Working through the four states shows what that actually costs, and it is less than it first appears in three cases and more specific in the fourth.

The model-response states are derivable already — the brain records that a request was sent and that a response began, and topology carries both to the face. Tool execution is derivable already — the limb records that a call started and how it exited. Waiting on the user is derivable already, from the turn's own state. So three of the four need no new facts at all; a caught-up face can compute them.

Harness internals is the one that needs something new, because nothing in the design currently records it. An MCP service initialising, a tool result being processed, conversation history being reordered — these are internal operations that produce no context fact and no execution fact, so a face has no way to know they are happening. The requirement the throbber forces is therefore precise: **internal operations must emit start and end facts into the stream.** Which operations deserve one is a judgement — MCP init and history reordering clearly do, every small reconciliation step probably does not — and that judgement is a question below.

The user confirmed this reading and said it was close to the throbber's purpose all along (2026-08-04): "it was kind of the point of the throbber in a way. Well, the point is to expose the internals, to tell you really what's going on right now in this session... are we waiting on a provider API request call? Are we waiting on the model to finish streaming? Are we waiting on a tool call? Are we waiting on the user?... the throbber is absolutely intended to expose this and therefore require that the harness can know about this stuff itself." Note that "require that the harness can know about this stuff itself" is exactly the internal-operations requirement — the harness cannot report a wait it never recorded. And a bar for the design: once the waits are facts, "it's clear that the throbber should be easy to implement" — if implementing it is hard, the state model is wrong, which is the test restated as a smell.

The visual approach is explicitly unresolved and wants exploration, and the user's own sketches should be preserved rather than narrowed: "maybe a little pentagon or square with small icons, where the icons flash or fade to indicate the current state. I don't know if that works"; "a small braille-style spinner with an icon next to it"; "maybe we have five different braille spinners, and a little pulse or 'zip' moves between them ... a line connecting the states where a pulse travels along the border, or the border thickens as the pulse moves between the different braille spinners". And: "I'm not sure. We should probably explore a variety of designs here." The requirements that constrain the exploration are that it be compact and that the meaning of the different states be obvious.

### What the exit condition actually needs

The exit condition has two halves that are easy to run together, and separating them is worth the paragraph, because one half is nearly free and the other is a web GUI — which the notes' non-goals list as "Better web UI (not yet — OpenCode already sets a high bar here)".

The claims divide. Everything the state model asserts is about **two clients**, not two renderers: that shared-live state reaches both, that a freshly attached one renders correctly from catch-up alone, that a stale send from one is recognised, that a draft converges. Two instances of the TUI on one session exercise all of it — and that is a fixture topology already requires as `face ↔ brain+limb ↔ face 2`, so it costs this experiment nothing to arrange. User-turn reaches the same conclusion from its own side: two faces in one process is what makes the multi-client half testable at all.

What a second *renderer* would additionally prove is narrower: that the state model is not accidentally shaped around a terminal — that nothing in it assumes character cells, a single focused pane, or synchronous redraw. A **headless client** proves that better than a web GUI does, because it can assert the property directly: attach mid-session, derive the complete view from catch-up, and report it as data rather than as pixels. If the state model can feed something with no renderer at all, it is not TUI-shaped.

So the exit condition is two TUI instances plus one headless catch-up-asserting client, and no web renderer is needed to close it. The web GUI remains a real goal — the tech notes offer a route worth remembering when it becomes real, since Deno has an "(experimental?)" Tauri-like option that would keep the GUI in-process in the decoupled monolith — but it is a consumer of a proven model rather than part of the proof.

### Putting it back together

The design is one classification plus two mechanisms. The classification asks, of every piece of UI state, what breaks if another client does not know it — and sorts the answers into state that stays on one screen, state two clients must agree about while the user is working, and facts that become the session record. The first mechanism gives every client send a causal position, so that a client acting on stale information is a representable fact rather than an indistinguishable write, which makes both reconnect-without-duplicates and never-losing-text ordinary rather than special. The second mechanism is structural rather than procedural: shared-live state is a class the model-facing projection never selects, so the rule that drafts never become context is enforced by the shape of the code and observable in `/dump`. Everything else — how the draft converges, where it is physically stored, what the throbber looks like, how the scrollbar's end caps work — sits on top of that and can change without disturbing it.

The thesis is that one client state model, with those three classes and causally positioned sends, is enough for any number of clients to share a session while the user moves between them — a real reactive TUI being the first of them and a web GUI a later one. It is falsified by: any piece of the view that a freshly attached client cannot derive from catch-up; a stale send that either silently overwrites newer state or is silently discarded; a reconnect that duplicates or drops the user's input; any character of shared-live state appearing in a provider request, or appearing in `/dump` without being marked invisible; face-local state that turns out to need replicating, or shared-live state that turns out to differ legitimately per client; or a second consumer that can only be made to work by adding state paths the first one did not need. The invariants in play are 3 (an event is about its emitter, consumers project it), 5 (durable, cache-supporting-transient, shared-UI and disposable data explicitly distinguished), and 7 (stale clients cannot silently overwrite; the user wins), with 10 relevant wherever one face would otherwise assume something about another's environment.

## Interactions

This design lives in the events-and-transport cluster but owns the smallest part of it, and stage 3's most useful outcome here is subtraction: quite a lot of what looked like this experiment's problem belongs to a sibling that has already designed it. `INTERACTIONS.md` holds the portfolio view of the shared machinery; this section says what is owned, what is inherited, and what turned out to be nothing.

### The substrate is topology's; the convergence is this design's

The ordered stream, the per-client resume point, the handshake in which a joining peer declares itself and catches up, and the mechanism by which a send carries the causal position of its sender all belong to topology, which needs every one of them independently — a cancellation cannot be an in-memory token handed across a role boundary, so causally positioned facts get built there whether or not the UI case exists. **This experiment inherits that mechanism and does not design it.** What it owns is everything the mechanism does not decide: which class a piece of state belongs to, the fact-versus-live-state line, what happens to a send once it has been recognised as stale, and how a draft buffer converges.

That is a real reduction in scope, and it changes what the experiment builds. The causal machinery is not this design's risk; the *policy* is, and the policy is where invariant 7 runs out of content.

One unresolved question underneath topology reaches through, and it is worth being careful about what it does and does not decide. Whether same-machine IPC is close enough to sequence is open, and topology's position is that in the absence of evidence the answer is no. What that does *not* change is whether causally positioned sends are needed: why #1's motivating story is a phone, so the mechanism was mandatory before the IPC question was asked, and it stays mandatory whichever way the verdict goes. Nor does it mean an unordered world — the brain sequences proposals into facts in every deployment, which is this design's own mechanism.

What the verdict does affect is *latency*, and latency lands squarely on the part of this design that is genuinely hard. If a client cannot cheaply await confirmation that its send was sequenced, it must show the character first and reconcile afterwards, so more rebase work becomes visible to the user. That is an input to choosing among the three convergence candidates below, not to whether the mechanism exists. It is also why the same-machine and phone cases are not interchangeable: they differ by orders of magnitude on exactly the axis that decides whether local echo feels right.

The other direction produces one requirement that this design hands *to* topology. A face that has just attached must render the correct waiting-state from catch-up alone. Most of that is already satisfied by facts topology carries — request sent, response began, tool started and exited — but the throbber's harness-internals state is recorded nowhere, so **internal operations have to emit start and end facts**, which is an addition to what crosses the brain→face boundary. It is the one piece of the UI content below that earns a place in this experiment, and it earns it as a test rather than as decoration.

Topology and this design are *not* a merge candidate, despite sharing the `face ↔ brain+limb ↔ face 2` configuration outright. They make different assertions on the same fixture: topology asserts that the durable record comes out the same, and this design asserts that the rendered view comes out the same. Two assertions on one fixture is an argument for sharing a scenario, not for sharing a thesis.

### Where shared-live state actually lives

Persistence-analytics answers a question this doc leaves open, and for a reason of its own rather than one borrowed from here. Its proposal is that shared-UI state is **checkpointed rather than journalled**: a small table keyed by session, overwritten in place, outside the append-only log, never analysed, never projected to the model, dropped when the session ends, and carrying whatever causal token this design needs so a stale face cannot clobber newer state. The reasoning is about churn — a draft buffer mutates on every keystroke, and mutable rows in an append-only log destroy the log's rebuild property, which is the one thing that log exists for.

So the division is: **persistence owns the checkpoint table and its durability; this design owns what the causal token means and what happens when it is stale.** The class is unchanged by the storage shape — shared-live state is still not history and still not model-visible, and it is still the model projection's silence rather than the table's location that guarantees the second of those.

Worth noting the boundary of persistence's argument, since it applies to churn rather than to the class as a whole. It fits the draft buffer well. It has nothing to say about anything derived, which is why the waiting-state stays out of the table and out of the class: a value any caught-up client can compute does not need storing anywhere.

There is also a genuine disagreement, left pointing at persistence rather than resolved here. This doc's classification treats shared-live state as live rather than durable; persistence argues that draft text is the one piece of it a user would be annoyed to lose across a brain restart, so it should survive one. Those are different claims and only the second needs durability: "the phone renders the same draft" and "the draft survives a brain restart" are separate tests, and this experiment can prove the first without ruling on the second. Persistence's own questions carry the ruling — and note that if it is ruled durable, shared-live state becomes a second instance of durable-but-never-projected alongside oauth's refresh tokens, which is the case persistence's two-axis split of invariant 5 exists to express.

### User turn draws the same line, and bounds the hard part

This is the densest connection in the section and it is mostly good news.

The first open question in this doc asks where the line in why #4 falls: a file the user has open looks like both shared UI state and context that user-turn wants the agent to see. User-turn drew that line independently and drew it the same way — a durable fact about what the user did, projected to the model, and live view state that is never projected — and explicitly assigns the live half onward: what stays face-local is the editing buffer, the unsaved state, the cursor and the scroll position, "and, where it needs to be shared between clients, multi-client-ui's problem". So two designs converged on the same boundary from opposite ends, which is the strongest evidence available that it is the right one. The question below stays, because the user has not ruled, but it is no longer an open design problem.

User-turn's harder ruling is what bounds this design's difficulty. Reads and writes go through the limb even when the face and limb share the user's machine — for remote limbs, for limb-owned truncation, and because the limb records execution facts. That leaves the editing buffer as the *only* file state on the face's side, which is precisely why shared-live state is a handful of things rather than an entire UI. If user-turn had let the face touch files directly, the shared-live class would have had to carry file contents and this experiment would be much larger.

The scoping call that follows is that **this design owns the classes and the convergence mechanism; each user tool owns its own live-state shape and its own two projections.** User-turn generates most of the shared-live state — which tool is open, the terminal's live state, the search state — and enumerating it here would duplicate user-turn's work and go stale. So the experiment proves the mechanism on the smallest sufficient case: a draft buffer plus one open file.

One case belongs to neither doc yet and falls out cleanly once both are read. User-turn's three-state input scheme accumulates *staged parts* that have been committed to the turn but not sent, and it separately rules that staged text does not piggyback to the model while activity does. By this design's own test — has the thing finished being true? — staged parts are shared-live: the phone should show them, because losing them is exactly the failure why #2 is about. And they are never projected, because user-turn says so for its own reasons. So staged text is a clean new instance of shared-live-and-never-projected, discovered from the interaction rather than from either doc. It is added to the class below as a proposal.

Finally, user-turn hands over one case explicitly: whether the *user's* editor should tell him that the agent has modified a file underneath him. Invariant 7 says the user wins, so his write is never rejected, but "the user wins" and "the user is never told" are different things. That is a UI concern and this design accepts it — the negative rule extends naturally, since a divergence the user cannot see is the same failure as text discarded silently.

### The renderers are soft middle, which is a second route to the exit condition

Self-modification's boundary puts the rendering framework in the shell and pretty much all UI content — even the TUI content — in the soft middle. Applying its own classification test to this design's parts is more useful than restating the boundary. The state model is depended on by a peer process and by a stored row, so **the state model is shell**; a renderer merely fits into it, so renderers are soft middle.

That is the layering reaching the same place the what reaches on its own reasons. What has to be got right once, and is expensive to get wrong, is the shell — the state model. Consumers of it are cheap and replaceable, which is exactly why proving the model does not require an expensive consumer: two instances of one renderer plus a headless client exercise the shell as thoroughly as two renderers would. It also explains why the scrollbar's half-block end caps matter more than a styling detail suggests: opentui-rust is the rendering framework, so it is shell, so changing its primitives is a shell change and fork-versus-upstream is a real decision rather than a preference.

### Operator lifecycle: a stale tab, and a face that leaves

Two connections, both small and both concrete.

A browser tab that has been open for days is operator-lifecycle's canonical *report* case — a face is not deployable from the brain, so a version mismatch can only be told to the user, who reloads and reattaches. The consequence for this design is a state it does not currently have: reconnect has to distinguish "catching up" from "refused, reload required", and the second has to be visible. Reconnect is otherwise ordinary here by design, so this is the one place where it legitimately is not.

Detach resolves in this design's favour and closes an open question of operator-lifecycle's. It asks whether a detaching face's local state is discarded or handed to another face, and calls that multi-client's question. The taxonomy answers it: face-local state is by definition not worth handing over, since another face on another screen size actively does not want it, and shared-live state is already shared, so there is nothing to hand. **Detach costs nothing at the state level.** That is a pleasing consequence of the classification rather than a mechanism, which is some evidence the classification is carrying weight.

### The cells that stayed empty, and what that licenses

Limb-model and this design barely interact, which `INTERACTIONS.md` records at the portfolio level. Both are about where things live, but one is about environments for agents and the other about views for humans, and they meet only through topology. There is nothing to coordinate.

Forked-subagents contributes the session switcher and the button that launches a user-facing session into a scope, and both look like UI state until they are classified. They are projections of durable session state — scopes, sibling status, the work map — so they need nothing from the shared-live model and nothing from the convergence mechanism. The user's button is a client-originated send like any other and inherits topology's causal positioning without a special case.

Context-updates, compaction-handover, cancellation-economics and oauth-credentials are empty against this design. That is worth recording rather than passing over, because it is what makes this experiment independent of the tight cluster around context and cache: it depends on topology and persistence and on user-turn's boundary, and on nothing else.

The TUI styling material is the largest genuinely inert block in this doc, and honesty is better than manufacturing links for it. The Anthropic colour scheme, the one-row-equals-two-columns geometry, the half-block transitions, and the never-achieved Windows-style persistent select connect to nothing except self-modification's soft-middle boundary, and they are a port of a change the user has already made in his OpenCode fork rather than a design. Only the throbber earns a connection, and only as the catch-up test above. Read from the interaction side, that is the answer to this doc's third question: the styling work can be deferred without blocking anything at all.

### Conflicts recorded elsewhere

One conflict involving this design is recorded in `INTERACTIONS.md`: invariant 7's "the user wins on conflicting edits" resolves user-versus-agent and does not reach the user-versus-user case this experiment is actually about. Reading the invariant's other clause narrows that — "stale clients cannot silently overwrite newer state" does settle who may win — so what stands open is only the added clause about the losing branch, which the what proposes and the questions below carry.

## Questions for review

- Where exactly is the line in why #4? A file the user has open is arguably both shared UI state *and* context that user-turn wants the agent to see. Same datum, two classes — or two different events?
- Is a CRDT worth it for the draft buffer given a session-authoritative brain already exists, or is last-writer-wins-with-causal-rejection enough for a single user moving between his own devices?
- Should the TUI styling work happen here, or wait until the state model is proven and be its own pass? It is appealing to do and not load-bearing. The throbber is the exception, and it is load-bearing *as a test* rather than as UI.
- **Which internal operations deserve a start/end event?** The throbber's harness-internals state is the one part of it nothing currently records, so internal operations have to emit facts. MCP initialisation and history reordering clearly warrant one; a small reconciliation step probably does not, and emitting one per step would flood the stream for no gain. The line is yours — the same line you drew for change notices, and for the same reason.
- **One clause added to invariant 7, not a replacement for it.** Its first clause — stale clients cannot silently overwrite newer state — already settles the phone-versus-desktop case. What it leaves open is the losing branch, so the what adds: no branch of your own text is ever discarded silently either; a stale send may be rejected, merged or superseded, but the losing text stays recoverable and the divergence is visible. Is that the clause you want?
- **The exit condition needs two clients, and one non-TUI consumer, but not a web GUI.** Two TUI instances on one session exercise everything the state model claims, and that fixture is topology's `face ↔ brain+limb ↔ face 2` which exists anyway. A headless client that asserts it can derive the whole view from catch-up proves the model is not TUI-shaped, which is the only thing a second renderer would add. Confirm, because it decides whether a web front-end is in this experiment at all — the notes' non-goals say "Better web UI (not yet — OpenCode already sets a high bar here)".
- The what proposes an answer to the first question above — that an open file yields two events in two classes, the finished fact (durable, projected to the model) and the live view state (shared-live, never projected), distinguished by whether the thing has stopped changing. Does that line sit where you want it?
- The scrollbar's configurable half-block end caps are a change to opentui's own primitive. Fork it, contribute upstream, or work around it?
- Windows-style persistent select with right-click copy and paste was never achieved in the OpenCode fork. Is it in scope for this experiment, or a known-hard item to attempt once the TUI exists?
- **Staged text is proposed as a new member of the shared-live class**, found while working the interactions with user-turn. Parts you have committed to a turn but not sent should appear on your phone (losing them is exactly the failure why #2 is about) and are never projected to the model (user-turn rules that staged text does not piggyback). Clean instance of the class, but neither doc had assigned it.
- **The draft buffer is proposed to live in persistence's checkpoint table** — a mutable row overwritten in place, outside the append-only log — because it churns on every keystroke and mutable rows would wreck the log's rebuild property. That is persistence's design; this experiment would own only what the causal token means. It also means the two designs currently disagree about whether draft text survives a brain restart; persistence says it should, this doc's classification says live-not-durable. The ruling lands in persistence's questions, but it changes what this experiment tests.
- **This experiment inherits causally positioned sends from topology rather than designing them**, and owns only the policy for what to do with a stale one. Worth being clear that the mechanism is required by why #1's phone regardless of how topology's same-machine IPC question resolves; what that verdict changes is how much rebase work is visible during local echo, which is an input to the convergence choice above.
- **Reconnect needs a state this doc does not currently have.** Operator-lifecycle refuses a stale face's connection and tells the user to reload; so catch-up has to distinguish "catching up" from "refused, reload required", visibly. Everywhere else reconnect is deliberately ordinary, so this is the exception.
- **The state model is shell, the renderers are soft middle** — by self-modification's own classification test, since a peer process and a stored row depend on the state model's shape and a renderer only fits into it. That is a second route to the exit condition above: what has to be got right once is the shell, and content sets are cheap. It also means opentui's scrollbar end caps are a shell change, which is why fork-versus-upstream is a real decision.
